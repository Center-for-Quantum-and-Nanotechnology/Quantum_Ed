This section continues Module 05 — Quantum Software Stack. 05.03 ended by asking where a target's list of what it allows comes from, and whether it can change. This page answers that and opens up the backend-description and Control Layer responsibilities from 05.01. ________________________________________
Goal
Teach the learner that software describes each target to itself, that this description tells software what the target allows and, for a device, what has been reported about its current condition, and that reported values are time-stamped estimates which can change and are not guarantees.
The central progression is:
A TARGET'S LIST COMES FROM A DESCRIPTION → A DESCRIPTION SAYS WHAT A TARGET ALLOWS → A DEVICE IS CALIBRATED BECAUSE ITS BEHAVIOR DRIFTS → CALIBRATION TELEMETRY REPORTS ESTIMATES WITH A TIME → SOFTWARE MAY USE THEM UNDER A POLICY
The learner should understand that a target is not just a list of allowed operations: it is a description that software reads.
The key conceptual transition is:
“A target is not just a list of allowed operations. It is a description that software reads, and for a device the description can include time-stamped estimates of how each part is doing. Those numbers inform decisions. They do not guarantee outcomes.”
This section should prepare the learner for Simulation Engines and Methods (05.05).
________________________________________
Learning Outcomes
By the end of the section, the learner should be able to:
	Explain that software reads a backend description of a target to learn what it allows, and that this is where a target's list of operations comes from.
	Name what a description of a target communicates: supported operations (native gates), which qubits can be used together (connectivity), and the kind of target.
	Distinguish a simulator target from a hardware device target, including that a simulator has no calibration data because nothing physical is calibrated.
	Distinguish calibration (a procedure that characterizes and tunes a device) from calibration telemetry (information reported about its condition).
	Explain why devices are calibrated and why reported characteristics change over time (drift), including that change is not always for the worse.
	Describe the boundary between application-facing software and device-control software, and recognize that control settings exist without being taught or exposed here.
	Read a small set of telemetry fields, with units: operating frequency, T1, T2, gate error, readout error, and what each is an estimate of.
	Explain that each reported value carries a time, a status, and an uncertainty, and that a number without them can mislead.
	Distinguish what was reported, what it means, and what software might do about it, and say that a response depends on a policy.
	Explain that a metric is not a guarantee: T1, gate error, or readout error alone does not say whether a whole circuit will succeed.
	Explain that reported data may be old, incomplete, or estimated, and that not every device reports every field.
	Distinguish backend metadata from raw control signals, and drift from automatic adaptation.
	Ask how a simulator, as one kind of target, works out its answer.

Page Structure
1. From Transformation to Targets
Begin directly from the Compilation and Transpilation material.
Revisit the familiar progression:
A FORM SAYS WHAT TO COMPUTE
↓
SOFTWARE REWRITES IT FOR A TARGET
↓
THE REWRITE DEPENDS ON THE TARGET'S LIST
Show the three targets from 05.03 (Open, One-way CNOT, Rotations), each with its list of what it allows.
Then ask:
“Where does a target's list of what it allows come from, and could it change?”
Answer in one sentence: software reads a description of the target.
Name what the page covers, in order: what a description says, then what a device additionally reports and why that changes.
The learner should see a target as something software is told about, not something software already knows.
Do not repeat the 05.01 explorer or the 05.03 explorer.

2. What a Backend Description Tells Software
Introduce the backend description as the place where the Application and Control groups meet, as defined in 05.01.
Clearly distinguish:
	Backend description — what software is told about a target.
	The target itself — the simulator or device that carries out the work.
Say what a description communicates:
	what kind of target it is
	which operations it allows (native gates)
	which qubits can be used together (connectivity)
Show the three 05.03 targets again, now named as descriptions: the same lists.
Say that a description is an abstraction. It is not the device, and it is not raw control signals.
Include a short explanation such as:
“Is the description the same thing as the device?”
“No. It is what software is told about the device.”
Do not imply that a description contains everything about a target.

3. Simulator Targets and Device Targets
Reconnect to the execution target from 05.01.
Both kinds of target have descriptions. They say different things.
Show the explorer's two targets, side by side, each labelled as synthetic:
	Simulator — a classical program. Its description lists supported operations and says that its limits are set by the classical computer running it. It has no calibration data, because nothing physical is calibrated.
	Device Q4 — a small invented device. Its description lists supported operations, which qubits are connected, and what has been reported about its condition.
Add one hedged sentence: a simulator can be configured to imitate a device's reported properties, which is a choice and not a default.
The learner should understand:
BOTH ARE DESCRIBED
↓
BUT A DEVICE HAS A PHYSICAL CONDITION TO REPORT
Do not give numbers for the simulator's limits. Do not name any simulator. Simulation methods belong to 05.05.

4. Why a Device Is Calibrated, and Where the Control Software Sits
Introduce calibration as a procedure that characterizes and tunes a device.
Explain conceptually:
A device's behavior can drift, so the procedure is repeated.
Place the control software with the Control Layer from 05.01:
	Control software runs calibration and sits beside the device.
	Application-facing software sits on the other side of the backend description.
Show a short flow:
CALIBRATION PROCEDURE
↓
MEASURED OR ESTIMATED VALUES, WITH A TIME
↓
A REPORT
↓
THE BACKEND DESCRIPTION
Make the contrast explicit:
	Calibration is something that is done.
	Telemetry is information that is reported.
Show control settings as one labelled row: “Control settings: exist on the device; not reported here and not taught on this page.”
Say once that the physical reasons for drift belong to the Quantum Hardware module. Add no link.
Do not teach calibration physics, measurement protocols, pulse design, or control electronics.
Do not imply that application software talks to control electronics.

5. Reading Calibration Telemetry
Introduce a small set of fields, in cards or a table. For each, show what it conveys, its unit, and what it is not.
	Operating frequency (GHz) — a device-specific frequency relevant to control and characterization. Label it modality-specific.
	T1 (µs) — a characteristic timescale for energy relaxation. Not the chance that a circuit succeeds.
	T2 (µs) — a characteristic timescale for phase coherence. Definitions and protocols differ; T2 and T2* are not interchangeable.
	Single-qubit gate error (%) — an estimate under a particular procedure. Depends on protocol and time.
	Two-qubit gate error (%), per connected pair — the same, for a pair.
	Readout assignment error (%), shown as two numbers: a qubit prepared in 0 read as 1, and prepared in 1 read as 0. May be asymmetric, and is not the same as gate error.
	Native operations and connectivity — capability metadata. Tends to change less often than calibration metrics.
	Control settings — named only.
Mark every value synthetic.
Say that other hardware types report different fields, and that no device reports every field every time.
Then introduce provenance: a value comes with a time, a status, and an uncertainty. Show a number with and without them, and ask which one can mislead.
The learner should understand:
A NUMBER
↓
WITHOUT A TIME, A STATUS, AND AN UNCERTAINTY
↓
CAN MISLEAD
Do not present the fields as a standard schema. Do not assert real ranges or typical values.

6. Main Interactive — “Backend and Calibration Explorer”
Make this the primary V1 interaction.
Allow the learner to choose a target and, for the device, which snapshot the software has.
At minimum support:
	Choosing a target: Simulator or Device Q4, each with a one-line description and labelled synthetic.
	Choosing a snapshot for the device: Earlier or Later, each labelled with its synthetic time (“06:00” and “18:00, same day”). For the simulator, show the control disabled with the reason: “a simulator has no calibration data”.
	Selecting a qubit or a connection on the device map.
	A view toggle, “Compare the two snapshots”, showing each value's change.
	Resetting the view to its starting state.
Frame the snapshot choice as “which report the software has”. Choosing the earlier snapshot while a later one exists shows software working from older data, with its age stated.
When the learner chooses a target, a snapshot, or an item:
	Show the backend description in its own card: kind, operations, and connections.
	Show Reported (teal dashed, tagged “reported”): the selected item's values with units and uncertainty, the snapshot's time and status, and “not reported” where a value is missing.
	Show What it means: a plain sentence per field, always with its qualification.
	Show A possible response (dotted border, tagged “one possible policy”): for the Bell circuit, the connected pair that each of two stated policies would choose from this snapshot, and a sentence that this ranks reported numbers and is not a prediction.
Keep what the learner chooses (target, snapshot, selection) separate from what is derived (the description and the three panels) and from what is observed (a value moved, the policies disagree, the best pair changed).
The learner should visually experience:
CHOOSE A TARGET AND A SNAPSHOT
↓
SEE WHAT WAS REPORTED, WHAT IT MEANS, AND A POSSIBLE RESPONSE
↓
NOTICE THAT VALUES CHANGE AND POLICIES DIFFER
Reinforce the distinction established in 05.01:
Reported information may inform software. Whether and how it does depends on the platform.
Make the interaction resettable and keyboard accessible. Make the device map's qubits and connections focusable buttons with text labels. Announce a change of target, snapshot, or selection in an aria-live region. Provide the comparison as a list of sentences. Keep focus where it was after the view re-renders.
Include these checks:
	Prediction task: “Under the policy ‘lowest two-qubit error’, which pair will the later snapshot choose, compared with the earlier one?” Offer the three pairs, then compare with the explorer.
	Conceptual question: “A qubit's reported T1 is long. Does that mean a circuit using it will succeed?” Give feedback on each wrong choice: a metric is a timescale estimate, not a guarantee; other errors matter; the value has a time.
	Transfer task: “Software has the earlier snapshot, and the later one now exists. What might go wrong if it uses the earlier one?” The values may have drifted, and the best pair may have changed.
Do not add a real device or vendor, real field names or an API, pulse or control values, live data, routing, or a success prediction.

7. A Metric Is Not a Guarantee, and Telemetry Is Not Live Truth
Make the distinctions explicit, in a contrast block.
Calibration ≠ telemetry
Calibration is a procedure. Telemetry is reported information.
A metric ≠ a guarantee
A whole circuit's success depends on much more than one number.
Telemetry ≠ real-time truth
Values may be periodic, old, estimated, filtered, or missing.
Backend metadata ≠ control signals
A description is an abstraction.
Drift ≠ automatic adaptation
A response depends on the platform, its data access, its policies, and its software.
Use the explorer to show that:
A reported number is a time-stamped estimate, not a promise.
Do not imply that all telemetry is continuously streamed, or that all fields are available on every device.

8. From Reported Numbers to Possible Decisions
Bring back the Bell circuit and ask:
“Which connected pair could it use?”
Show two stated policies, each choosing a pair from the same snapshot:
	Lowest two-qubit error on the pair.
	Lowest sum of the pair's two-qubit error and both readout errors.
Show that the two policies can disagree in the same snapshot, and that the same policy can choose differently from the other snapshot.
The learner should understand:
THE SAME REPORTED NUMBERS
↓
UNDER DIFFERENT POLICIES
↓
CAN SUPPORT DIFFERENT DECISIONS
Say that many tools do not do this automatically, and that what software does depends on its policy and on which report it has.
Name once that choosing which physical qubits to use is part of what the glossary calls qubit mapping, which is Intermediate.
Do not teach mapping or routing. Do not show a success probability.

9. From Targets to Simulators
End by returning to the two targets in the explorer.
Previously:
A DEVICE REPORTS TIME-STAMPED ESTIMATES
↓
SOFTWARE MAY USE THEM UNDER A POLICY
versus:
A SIMULATOR HAS NO PHYSICAL CONDITION TO REPORT
↓
BUT IT IS STILL A TARGET THAT SOMETHING MUST COMPUTE ON
Ask:
“If a simulator is just another kind of target, how does it actually work out the answer, and why do different simulators behave differently?”
Then introduce the next problem: a simulator is a classical program that models a quantum computation, and different methods trade capability for cost.
Do not explain simulation methods here.
End with:
“If a simulator is just another kind of target, how does it actually work out the answer, and why do different simulators behave differently?”

Important Pedagogical Constraints
Do not imply:
CALIBRATION = TELEMETRY
Instead teach:
Calibration is a procedure. Telemetry is information reported about a device's state, quality, and settings.
Do not imply:
A METRIC = A GUARANTEE
Instead teach:
T1, gate error, or readout error alone cannot predict whether a whole workload succeeds.
Do not imply:
TELEMETRY = CONTINUOUS REAL-TIME TRUTH
Instead teach:
Values may be periodic, old, estimated, filtered, or missing, and each carries a time.
Do not imply:
BACKEND METADATA = RAW CONTROL SIGNALS
Instead teach:
A backend description is an abstraction that software reads.
Do not imply:
DRIFT = AUTOMATIC ADAPTIVE COMPILATION
Instead teach:
A response depends on the platform, its data access, its policies, and its software design.
Do not imply that any device reports every field, or that the fields shown are a standard schema. Fields differ by hardware type and provider.
Do not imply that the synthetic device or its numbers are real, typical, or any vendor's.
Do not imply that lower error or longer T1 is simply better for a whole circuit, or that drift always makes things worse.
Do not imply that a simulator and a device are described the same way, or that a simulator has hardware properties.
Do not imply that the Control Layer and the backend description are the same thing, or that application software talks to control electronics.
Do not teach calibration physics or measurement protocols, pulse design, real vendor schemas or APIs, hardware-aware decoding, routing or qubit-mapping algorithms, simulation methods, job lifecycles, or any real SDK behavior here.
Keep Beginner V1 focused on the mental model required to read reported device information correctly and to understand what a simulator is a target of.
