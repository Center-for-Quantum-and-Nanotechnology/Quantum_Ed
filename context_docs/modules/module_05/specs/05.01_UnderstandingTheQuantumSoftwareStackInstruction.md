This section opens Module 05 — Quantum Software Stack. It assumes the learner has introductory familiarity with quantum programming, SDKs, simulation, and submitting computations to hardware. Do not require mastery of any particular SDK.
Module 05 uses an architecture-driven taxonomy taught through the journey of a familiar quantum program. This opening section establishes the system-wide mental model; later pages own the technical details of individual responsibilities.
________________________________________
Goal
Teach the learner why a quantum program depends on multiple interacting software responsibilities between writing code and obtaining useful results.
The central progression is:
FAMILIAR QUANTUM PROGRAM → SOFTWARE RESPONSIBILITIES → EXECUTION PATH → RESULTS
The learner should understand that the code they write is one entry point into a broader software system, not a complete description of everything required to execute a quantum computation.
The key conceptual transition is:
“Running a quantum program is not one software action. It is a coordinated set of responsibilities that describe, adapt, execute, and return the results of a computation.”
This section should prepare the learner for Quantum Program Representations (05.02).
________________________________________
Learning Outcomes
By the end of the section, the learner should be able to:
	Explain why quantum programming requires supporting software beyond the code written by a user.
	Identify a quantum program as an input to a broader software workflow.
	Recognize the major responsibilities of program representation, compilation, backend description, simulation or hardware execution, runtime coordination, and result handling.
	Describe, in plain language, what each responsibility contributes without explaining its implementation.
	Distinguish a software responsibility from a particular vendor product, library, or deployment component.
	Trace a simple quantum computation from a familiar program to returned measurement results.
	Recognize that simulation and hardware execution are different paths that can share software responsibilities.
	Explain that the responsibilities interact and do not necessarily form one fixed linear pipeline.
	Recognize that classical software coordinates many parts of quantum computation.
	Ask why the same computation may need different representations as it moves between software responsibilities.

Page Structure
1. From Running a Program to Asking What Happens
Begin with a familiar Module 03 action: write or construct a simple Bell-state circuit, select a simulator or hardware target, run it, and inspect measurement results.
Revisit the familiar progression:
WRITE A CIRCUIT
↓
RUN IT
↓
SEE RESULTS
Then ask:
“What happened between pressing Run and receiving those results?”
Explain that Module 03 emphasized using quantum software; Module 05 examines the software responsibilities that make that use possible.
Do not reteach Python environments, Jupyter, VS Code, or the SDK APIs.
Use a compact familiar circuit depiction; do not require live SDK execution.

2. Meet the Software Stack
Introduce the quantum software stack as a useful way to organize cooperating software responsibilities.
Clearly distinguish:
	User program / application — expresses the computation the user wants to perform.
	Program representation — expresses the computation in a form software can process.
	Compilation / transformation — adapts or optimizes a representation for an intended target.
	Backend / target description — communicates relevant execution capabilities and constraints.
	Execution engine or device — carries out a simulation or physical computation.
	Runtime / orchestration — coordinates execution, jobs, and exchanges with classical processing.
	Results — measurement data and other returned execution information for further interpretation.
Show these as responsibilities, not necessarily separate programs, servers, or mandatory sequential boxes.
Include a short explanation such as:
“Does every platform have exactly these seven layers?”
“No. These are responsibilities we can recognize across many systems. Real implementations may combine them, distribute them, or organize their interactions differently.”
Avoid claiming that a named SDK always owns one specific responsibility.

3. One Computation, Several Responsibilities
Keep the same Bell-state example visible while revealing what each responsibility contributes.
The learner should understand:
USER INTENT
↓
SOFTWARE DESCRIBES AND PREPARES THE COMPUTATION
↓
A TARGET EXECUTES IT
↓
SOFTWARE RETURNS OBSERVABLE RESULTS
Clarify that the circuit is an instruction or description, not itself a physical quantum state.
Use brief, concrete labels: “describe,” “adapt,” “check target,” “coordinate,” “execute,” “return.”
Do not introduce IR syntax, compiler passes, pulse waveforms, hardware physics, or a complete quantum execution protocol.

4. Main Interactive — “Follow the Quantum Program”
Make this the primary V1 interaction.
Present a familiar, static Bell-state circuit and an explorable diagram of software responsibilities.
Allow the learner to select a responsibility and choose between a conceptual simulator path and a conceptual hardware path.
At minimum support:
	Selecting each responsibility to reveal a short role description and its relationship to the example.
	Switching between simulator and hardware paths.
	Stepping through an illustrative journey from program submission to returned results.
	Resetting the view to its starting state.
When a responsibility is selected:
	Highlight the selected responsibility and relevant connections.
	Show the example's current conceptual artifact or action separately from the responsibility label.
	Show a concise explanation of what information is available at that point and what the next responsibility needs.
When the execution path changes:
	Show which responsibilities remain shared and which execution destination changes.
	Explain that the diagram is illustrative; real implementations can differ.
The learner should visually experience:
SELECT A PROGRAM AND EXECUTION PATH
↓
OBSERVE THE RESPONSIBILITIES INVOLVED
↓
SEE HOW RESULTS RETURN
Do not fabricate live job statuses, backend characteristics, execution timings, noise statistics, or hardware availability.
Use fixed, explicitly illustrative outcomes if measurement counts are displayed; avoid implying deterministic physical measurements.
Make the interaction keyboard accessible and resettable, and provide textual equivalents for highlighted relationships.

5. Two Paths, Shared Software Ideas
Extend the interaction by comparing a simulator execution path with a physical-hardware execution path.
Introduce the term:
	Execution target — the system selected to carry out the computation, whether simulated or physical.
The learner should discover that some software responsibilities apply to both paths, while the execution mechanism and relevant constraints can differ.
Ask:
“If both paths start with the same circuit, why might the software need different information before running it?”
Explain only that targets can have different capabilities and constraints.
Do not teach simulation algorithms, noise modeling, calibration, native gate details, or hardware control.
Do not imply that a simulator is always an exact replica of a particular physical device.

6. Responsibilities Interact, Not Just Stack Up
Revisit the simplified diagram and add a visible example of a relationship that does not follow a single straight line: backend capability information may inform compilation, and runtime coordination may span submission, execution, and results.
The learner should understand:
TARGET INFORMATION
↓
INFORMS PROGRAM PREPARATION
and:
RUNTIME COORDINATION
↓
CONNECTS EXECUTION AND RESULTS
Use a simple overlay or callout rather than a dense systems architecture diagram.
Make clear that “stack” is an organizational metaphor, not a requirement that information always flows strictly top to bottom.
Optionally allow a toggle between “simple learning view” and “interacting responsibilities view.”
Do not implement a real dependency graph or orchestration engine.

7. Software Responsibilities Are Not SDK Names
Reconnect to the tools introduced in Module 03, such as Qiskit, CUDA-Q, InQuanto, Stim, and qBraid, without asserting that each tool is a complete equivalent stack.
Explain that tools differ in scope and purpose; a framework, simulator, library, and platform may cover different subsets of responsibilities.
Ask:
“If two tools both let you work with quantum programs, must they perform the same jobs internally?”
Instead teach that architectural roles provide a way to compare tools without organizing the curriculum around a particular vendor.
Keep examples brief and avoid a product comparison matrix, installation instructions, or claims about current feature availability.

8. From the Stack to Program Representations
End by comparing the familiar programming view with the newly exposed software view.
Previously:
WRITE A CIRCUIT
↓
RUN IT
↓
READ RESULTS
Now:
DESCRIBE A COMPUTATION
↓
SOFTWARE COORDINATES SEVERAL RESPONSIBILITIES
↓
EXECUTE AND RETURN RESULTS
Present the Bell-state circuit again and ask:
“How can different software components understand the same computation if they do not all use the same form of program?”
Introduce the next problem: software needs ways to represent a quantum program at different stages.
Do not explain intermediate representations, serialization formats, or translation rules here.
End with:
“What does a quantum program look like after it leaves the code we wrote?”

Visual / UX Requirements
Reuse the established visual language of the existing repository and relevant Module 03 circuit displays. Inspect those implementations before choosing colors.
The Project Vision's Module 07 palette provides meanings that must not be contradicted:
	Blue → logical information / quantum state.
	Gray or neutral → physical qubits.
	Orange / red → noise and physical errors.
	Purple → syndrome / stabilizer / check information.
	Green → successful protection, recovery, or correction.
Module 05 does not yet have an established independent palette. Use neutral shapes and text labels for software responsibilities rather than repurposing these established colors arbitrarily.
Add clear visual distinctions for:
	User program.
	Software responsibility.
	Execution target (simulator versus hardware).
	Information passed between responsibilities.
	Returned results.
Do not rely on color alone.
The learner should be able to visually distinguish:
PROGRAM ≠ SOFTWARE RESPONSIBILITY ≠ EXECUTION TARGET ≠ RESULT
Keep the stack readable on smaller screens; prefer a vertically navigable, simplified layout over shrinking a dense diagram. Ensure selected states, paths, and explanatory text are accessible to keyboard and screen-reader users.

Important Pedagogical Constraints
Do not imply:
QUANTUM SDK = THE ENTIRE QUANTUM SOFTWARE STACK
Instead teach:
An SDK is a user-facing tool or set of tools that may expose or integrate several stack responsibilities.
Do not imply:
SOFTWARE STACK = ONE UNIVERSAL LINEAR PIPELINE
Instead teach:
The diagram is a teaching model of interacting responsibilities, which may be combined, repeated, or arranged differently across systems.
Do not imply:
SIMULATOR EXECUTION = PHYSICAL HARDWARE EXECUTION
Instead teach:
Both can support the same computational intent while using different execution mechanisms and constraints.
Do not imply that a quantum circuit is itself a physical quantum state.
Do not imply that compilation, backend selection, and runtime orchestration are interchangeable terms.
Do not imply that results always consist only of a single deterministic bit string.
Do not imply that all SDKs named in Module 03 provide identical functionality or interfaces.
Do not teach program-representation internals, transpilation algorithms, backend-property schemas, simulation methods, runtime internals, or quantum control software here.
Keep Beginner V1 focused on recognizing why those later topics are needed.

FAMILIAR QUANTUM PROGRAM
↓
RECOGNIZE MULTIPLE SOFTWARE RESPONSIBILITIES
↓
TRACE A CONCEPTUAL EXECUTION PATH
↓
UNDERSTAND HOW RESULTS RETURN
And understand the central relationship:
User intent → program description and preparation → coordinated execution → returned results.
The central takeaway should be:
A quantum program runs through a system of cooperating software responsibilities. Learning to recognize those responsibilities is the first step toward understanding how quantum software works beneath the programming interface.
