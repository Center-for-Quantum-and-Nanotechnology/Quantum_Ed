Goal
Teach the learner to follow one computation through every software responsibility on a simulator path and on a device path, to see what stays the same and what changes between them, and to recognize that the same responsibilities can be ordered, combined, and placed differently, so that what each step knows depends on when it acts.
The central progression is:
ONE COMPUTATION → THE SAME RESPONSIBILITIES AT WORK → A SIMULATOR PATH AND A DEVICE PATH → DIFFERENT ARRANGEMENTS OF THE SAME RESPONSIBILITIES → NO ONE UNIVERSAL ORDER
The learner should understand that a quantum software stack is a set of responsibilities, not a fixed pipeline, and that platforms differ in how they arrange, combine, and time them.
The key conceptual transition is:
“A software stack is not a fixed pipeline. It is a set of responsibilities, and different platforms arrange them differently, combine them, and decide when each one acts and what it knows.”
This section closes Module 05. It ends with a module recap and a question that points outward, not with a next page.
________________________________________
Learning Outcomes
By the end of the section, the learner should be able to:
	Trace one computation through the whole workflow, naming each responsibility and what it passes on.
	Say which responsibilities are the same on a simulator path and on a device path, and which differ.
	Explain what the device path adds: its software reports its condition, which may inform the description of the target.
	Distinguish Application Layer responsibilities from Control Layer responsibilities in a complete workflow.
	Recognize that the same responsibilities can be ordered, combined, or placed differently on different platforms.
	Explain that combining responsibilities in one tool hides the steps and does not remove them.
	Explain that what a step knows depends on when it acts, so an arrangement can change a decision without changing the kind of result.
	Explain that a device report can inform software only possibly, by policy, and not automatically.
	Place the calls of an unfamiliar tool onto the responsibilities without relying on its names.
	Say that SDKs, services, and products are not the same as responsibilities.
	Describe where a hybrid loop fits: it repeats the send-and-return part, with the classical side deciding between passes.
	Summarize Module 05 as a chain of responsibilities, and say what each page of the module taught.

2. One Computation, Step by Step
Introduce the steps as an ordered list, each tagged with its responsibility, its group, and the page that taught it (links within the module are allowed).
	Write the program — User program / application (Application Layer, 05.01).
	Describe it as data — Program representation (Application Layer, 05.02).
	The device’s software reports its condition — Device control and calibration (Control Layer, 05.04). Device path only.
	Check what the target allows — Backend / target description (where they meet, 05.04).
	Adapt the program — Compilation / transformation (Application Layer, 05.03).
	Send the job — Runtime / orchestration (Application Layer, 05.06).
	Run it — the execution target: a simulation method or the device (05.05, 05.06).
	Return the counts — Runtime / orchestration (05.06).
	Interpret them — Results (Application Layer, 05.06).
Nine steps on the device path, eight on the simulator path.
Say that the order shown is one order.
Do not re-teach any responsibility. Link each step back to its page.

3. Main Interactive — “Workflow Explorer”
Make this the primary V1 interaction.
Allow the learner to run the Bell circuit through a complete workflow and step through it.
At minimum support:
	Choosing a target path: Simulator or Device Q4, both the invented targets from 05.04.
	Choosing an arrangement: Prepare, then send; Send, then the service prepares; One tool does it all. Each has a one-line description.
	On the device path only: “A newer report arrives while the job waits”: No or Yes.
	Step, Back, and Reset.
Define the arrangements this way, labelled illustrative, with no vendor or product named:
	Prepare, then send — your tools describe the program, check the target, and adapt it, then send a job that already carries the adapted form. This is the 05.06 workflow.
	Send, then the service prepares — your tools send the program as written. The service checks the target and adapts it after receiving the job and after any wait.
	One tool does it all — one call performs every step, in the same order as Prepare, then send, combined into one visible action, with a “what happened inside” list that can be opened.
When the learner chooses a path, an arrangement, and steps through the workflow:
	Show the steps: the ordered list for this path and arrangement, each with its responsibility, group tag, who performs it (your tools, the service, the one tool), and a “done” or “now” mark.
	Show the step in focus: what it received and what it produced, taken from the model: the instruction list, the target’s description, the adapted list, the job and its status, the method or the device, the counts and the numbers made from them.
	Show what it knew, for the deciding steps (check and adapt): the report it had (its label and status), the stated policy, and the pair that policy would choose, labelled as a possible decision that is not applied.
	Show the result: the counts with their invented and simulated tags, the numbers made from them, and a sentence that the arrangement changed who did what and what a step knew, and did not change the kind of result.
Define the Control Layer’s part this way:
	On the device path, the report step produces the 05.04 calibration snapshot for the two connected pairs the page uses: its label, its status, and the reported values.
	The adapt step shows which connected pair the stated policy, “lowest two-qubit error”, would choose from the report that step has. The earlier report picks Q1–Q2; the later one picks Q0–Q1.
	Prepare, then send and One tool use the report available at preparation: the earlier one.
	Send, then the service prepares uses the report available after the wait: the later one only if the learner chose “A newer report arrives while the job waits: Yes”.
	Say plainly that this is a possible decision, that placement and routing are not taught here, that the chosen pair is shown but not applied to the circuit, and that the page does not model how the choice would change the counts.
Keep what the learner chooses (path, arrangement, report switch, steps) separate from what is derived (the steps and what each knew) and from what is observed (what stays the same across arrangements and what differs).
The learner should visually experience:
CHOOSE A PATH AND AN ARRANGEMENT
↓
WATCH THE SAME RESPONSIBILITIES ACT, IN THIS ORDER, BY THESE HANDS
↓
SEE WHAT EACH STEP KNEW, AND THAT THE RESULT IS STILL COUNTS
Reinforce the distinction established in 05.01:
A responsibility is a job that must be done. Who does it, and when, is the arrangement.
Make the interaction resettable and keyboard accessible. Controls are real buttons. The steps are an ordered list. Give each step a text description in words. Announce the step, who performs it, and what it produced in an aria-live region. Keep focus where it was after the view re-renders. Present tables as real tables, with stacked rows on a phone.
Include these checks:
	Prediction task: “Before you step through it: which responsibilities do you expect to differ between the simulator path and the device path?” The answer is the target, what describes it, the adapted program, and the report step; the rest is shared. Then compare with the computed table in subsection 4.
	Conceptual question: “A tool runs the whole workflow in one call. Does that mean it skips the responsibilities?” Give feedback on each wrong choice: it combines them and hides the steps, which still happen.
Do not add an SDK, routing or placement, a named platform, a timing, a noise model, or a hybrid-loop demonstration.

4. What Stays the Same, What Changes
Show a comparison of the two paths as a real table, computed from two builds, not written by hand.
Each row names a responsibility and says whether it is shared, differs, or exists on one path only:
	The program and its instruction list — shared.
	The report — device path only.
	The description — differs: the simulator’s limits, against the device’s operations, connections, and report.
	The adapted program — differs: the simulator keeps H; the device rewrites it as three turns.
	The job — differs: it carries the adapted form or the form as written, depending on the arrangement.
	The runtime’s lifecycle — differs: the device queues; the simulator does not.
	The method — differs: a simulation method, against the device.
	The results — the same kind (counts). The simulator can also give exact probabilities (05.05). The device’s counts include an invented share of off-pattern outcomes.
Say that most responsibilities are shared and that the differences cluster around the target and what is known about it.
Do not imply that the simulator path is the device path without the report.

5. The Same Responsibilities, Arranged Differently
Make the lesson of the arrangement control explicit.
Show a computed table of the three arrangements: the order, who performs each step, and what the deciding steps knew.
Include a short explanation such as:
“Combined is not removed.”
“A tool that does everything in one call still checks, adapts, sends, runs, and returns. It hides the steps. It does not delete them.”
Show the One tool arrangement’s inside, the same list of steps.
Explain that an arrangement can change a decision, the pair a policy would choose, because the step knew different information when it acted, and that this does not change the kind of result.
Say that these are three examples, not a complete list, and that no platform is claimed to work this way.
The learner should understand:
WHEN A STEP ACTS
↓
WHAT IT KNOWS
↓
WHAT IT MIGHT DECIDE
Do not imply that a later report means a better result.

6. Where the Hybrid Loop Fits
Keep this a short block. Do not build a second demonstration.
Say that the loop wraps the workflow: each pass is one run through send, track, and return, with the classical side deciding between passes.
Say that the explorer’s last step, interpret, may feed the next job.
Point back to 05.06 for the loop itself.
Do not rebuild the one-qubit rotation loop here.

7. Architecture, Not Products
Make the distinction explicit with a short “Map a tool” check, not a second interactive.
Describe two invented tools in a few lines each:
	One with separate calls to build, adapt, submit, wait, and fetch counts.
	One with a single call.
Ask the learner to place each call on the responsibilities.
Feedback names the responsibilities, never a product, and says what each tool leaves to the user.
Say that real tools differ in which responsibilities they expose, combine, or leave to the user.
Link 05.01’s block “Software Responsibilities Are Not SDK Names” rather than repeating it.
Do not compare real SDKs. The taxonomy places that at Intermediate or later.

Important Pedagogical Constraints
Do not imply:
THE STACK = ONE FIXED PIPELINE
Instead teach:
The page shows three arrangements of the same responsibilities, and none is the way.
Do not imply:
COMBINED = REMOVED
Instead teach:
A tool that does everything in one call still performs every step.
Do not imply:
A DIFFERENT ARRANGEMENT = A DIFFERENT KIND OF RESULT
Instead teach:
It changes who does what and what each step knew. The result is still counts.
Do not imply:
A DEVICE REPORT = AUTOMATIC IMPROVEMENT
Instead teach:
The report may inform a decision, by policy. The page does not model how the decision changes the counts.
Do not imply that the page’s arrangements are how any real platform works. They are examples, and the page names no platform.
Do not imply that a responsibility is a product or an SDK. Tools expose, combine, or leave out responsibilities.
Do not imply that the simulator path is the device path without the report. The target, the description, the adaptation, and the lifecycle differ too.
Do not imply that a simulator’s result is a forecast of the device’s (carried from 05.05).
Do not imply that a loop is better than a single run, and make no claim about quantum advantage.
Do not teach SDK use or comparison of real SDKs, named platforms, routing or placement, timings, noise models, algorithm design, error correction, or calibration physics here.
Keep Beginner V1 focused on the mental model that a software stack is a set of responsibilities that platforms arrange differently.
