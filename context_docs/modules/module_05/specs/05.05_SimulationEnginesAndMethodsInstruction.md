## Open questions for review

Each has a recommendation. Say which you accept or change; the rest of the draft already assumes the recommendations.

1. **Which methods does a Beginner see?** *Recommendation:* **three, each described by the same four questions** (what it keeps track of; what circuits it can handle; what makes it cost a lot; what it gives back): the **state-vector method** (keep every amplitude), the **stabilizer method** (keep a short list of rules that describe the state, for circuits built only from a restricted set of operations), and the **tensor-network method** (keep the state as small pieces joined by links, which is cheap when entanglement is low). Other methods exist (for example methods that keep more than a state so that noise can be included) and are **named in one sentence, not taught**. GPU acceleration, distributed simulation, and algorithm internals are Advanced.

2. **What does the main interaction compare?** The taxonomy asks for a "simulation-method comparison using carefully bounded, explanatory examples". *Recommendation:* a **Simulation Method Explorer**. The learner chooses a **circuit family**, a **number of qubits**, and a **method**. The page shows, in separate places: what the method **keeps** (and how big that is), whether it **can handle** the circuit (with the reason when it cannot), and what that means for **growth** as the circuit gets bigger. Three circuit families, so that no method wins everywhere:
   - **GHZ chain** (H on the first qubit, then a CNOT down the line; the Bell circuit when there are two qubits): restricted operations, low entanglement. Cheap for stabilizer and tensor network, doubling for state vector.
   - **GHZ chain with a T on every qubit**: one operation outside the stabilizer method's set, still low entanglement. The stabilizer method **cannot** handle it; the tensor-network method still can.
   - **Entangling layers** (alternating layers of single-qubit operations and neighbouring CNOTs, with a **depth** control): entanglement grows with depth, so the tensor-network method's pieces grow too.

3. **How much real simulation code?** The taxonomy says to avoid unnecessary full simulators. *Recommendation:* **small real engines for the two methods whose internals are short and checkable, and a measured driver for the third**, all pure and tested against each other, not a production simulator:
   - an **n-qubit state-vector engine**, run for up to **10 qubits** (1,024 amplitudes), using `QedGates` matrices at run time as `QedTrace` does;
   - a **stabilizer-table engine** for H, S, X, Z, and CNOT, which **refuses** any other operation and says which one;
   - for the tensor-network method, the **entanglement across the middle cut** computed from the real state vector (the number of independent pieces the state splits into across that cut), used as the link size; **no tensor-network engine**.
   Beyond 10 qubits the page uses **size formulas**, labelled "estimated from the method's size formula", never "computed". Everything the page calls "computed" was produced by running the engine at that size.

4. **How are costs shown without false precision?** *Recommendation:* show the **size of what the method keeps**, not time. State vector: **2ⁿ amplitudes** (and bytes, with Module 01's stated assumption of 16 bytes per amplitude, through `QedNumbers`). Stabilizer: a **table of about (2n)(2n+1) bits**. Tensor network (a chain of pieces): about **n × 2 × χ²** numbers, where χ is the largest link size. Say plainly: **size is not speed**; real speed depends on the implementation, the hardware, and more; the page gives **no timings, no benchmarks, no claim about any named simulator**. The qubit slider runs to 60, as on Module 01, so the learner can see the state vector's size pass anything a computer holds, with the tags "computed" (up to 10) and "estimated" (beyond).

5. **Where does the Bell circuit sit?** *Recommendation:* it **opens the page's central picture**. For two qubits the page shows the same Bell state **three ways, each produced by its engine**: the **four amplitudes** (state vector), the **two rules "XX" and "ZZ" that the state obeys** (stabilizer table), and **two small pieces joined by one link of size 2** (tensor network). This is the 05.02 idea again (one thing, several forms), now for what a simulator holds internally. The GHZ chain extends it to more qubits.

6. **Exact or approximate?** *Recommendation:* one hedged paragraph, no demonstration. The state-vector and stabilizer methods are exact for what they handle (up to rounding). The tensor-network method is exact when every link keeps its full size; real tools may **cap the link size to save memory**, which makes the answer approximate. The page does not show truncation.

7. **What does a simulator return, and how does it differ from a device?** *Recommendation:* a short, bounded section. A simulator **can show things a device cannot**: the whole state (Bell's four amplitudes) and exact outcome probabilities. A device returns **only samples**, one outcome per shot. A simulator can also **produce samples** the way a device does. By default a simulator models an **ideal** device. Simulating **noise** needs more than a state vector and costs more; the page says this in one sentence and ties it back to 05.04's sentence that a simulator can be set up to imitate a device's reported properties. **A simulator's answer is not a prediction of what a particular device will do.**

8. **Module 01's caveat and the exponential wall.** *Recommendation:* the page **picks up the caveat** on *Why Quantum Computing?* that clever classical methods exploit structure. It says the "2ⁿ wall" belongs to **one method**, not to classical simulation as a whole, and that structure (restricted operations, low entanglement) is what the other two exploit. It does **not** say which circuits are hard, whether a quantum computer can beat any method, or anything about quantum advantage.

9. **Where does the code live?** *Recommendation:* a **new pure module `QedSimMethods` (`sim-methods.js`)**: circuit families as data (an operation list for n qubits), the state-vector engine, the stabilizer-table engine, `cutRank` (entanglement across a cut), `sizes(method, family, n)` (the size formulas), a per-method **capability** record (what it keeps, what it handles, what drives cost, what it returns), `explain(family, n, method)`, and small renderers (a chain-of-pieces SVG, an amplitude table, a list of rules). It calls `QedGates` at run time for single-qubit matrices (tested with `loadModules`, as for `QedTrace`) and otherwise depends on nothing. `QedCircuit` draws the **two-qubit** Bell circuit only; larger circuits are shown as a short text description, not a drawing. Page-local: the explorer wiring, the contrast wording, and the checks.

10. **Experience levels.** *Recommendation:* as on 05.02 to 05.04, **V1 is Beginner-only, with no gated blocks**. Intermediate (future): the stabilizer method stated precisely (and the idea behind its efficiency), tensor networks with capped link sizes, methods that include noise, simulating measurement and sampling in more detail. Advanced (future): scaling analysis, GPU acceleration and distributed simulation, choosing among methods automatically, research-facing methods. Nothing above Beginner is tagged until built.

11. **Terminology.** Existing entries: **Simulator, Quantum Simulator, Stabilizer, Density Matrix, Noise Model, Shot, Sampling, Entanglement, Probability Amplitude, Measurement, Superposition**. *Recommendation:* reuse them, add this page to the references of the ones it substantively teaches (Simulator, Entanglement, Probability Amplitude, Shot, Sampling), and add **three** new entries: **State Vector** (the list of all amplitudes of a quantum state), **Clifford Circuit** (a circuit built only from a restricted set of operations; alias **Clifford gate**), and **Tensor Network** (a state held as small pieces joined by links). Do the full terminology check at build time and record it in `llm/FLAGS.md`. 12. **The simulator's limits from 05.04.** *Recommendation:* 05.04 said a simulator's limits "are set by the classical computer that runs it". This page **explains that sentence** for the state-vector method (the size of what it keeps) and says that other methods have **other** limits, so "how many qubits a simulator can handle" has no single answer: it depends on the method **and** on the circuit.

## Goal

Teach the learner that a classical simulator is a program that models a quantum computation, that there are several methods for doing so which keep track of different things, and that each method's strengths and limits come from what it keeps, so no single method suits every circuit and no single number says how many qubits a simulator can handle.

Central progression:

`A SIMULATOR IS A TARGET THAT MODELS THE COMPUTATION → THE OBVIOUS METHOD KEEPS EVERY AMPLITUDE AND DOUBLES WITH EACH QUBIT → OTHER METHODS KEEP LESS BY USING STRUCTURE → EACH METHOD HANDLES SOME CIRCUITS AND NOT OTHERS → CHOOSING A SIMULATOR IS CHOOSING A TRADEOFF`

Key conceptual transition: **"A simulator is not one thing. It is a family of methods, each keeping track of the quantum state in a different way, and the way it keeps track decides which circuits it can handle and what it costs."**

It opens by answering the question 05.04 ended on ("how does a simulator actually work out the answer, and why do different simulators behave differently?") and ends by asking the question that motivates 05.06.

## Learning outcomes (Beginner)

The learner should be able to:

1. Explain that a classical simulator is a program that models a quantum computation, and that it is one kind of target.
2. Describe the state-vector method: it keeps every amplitude, so what it keeps doubles with each qubit.
3. Explain that the 2ⁿ growth belongs to that one method, not to classical simulation as a whole.
4. Describe, conceptually, what the stabilizer method keeps (a short list of rules the state obeys) and that it handles only circuits built from a restricted set of operations.
5. Describe, conceptually, what the tensor-network method keeps (small pieces joined by links) and that it is cheap when entanglement is low and grows as entanglement grows.
6. Recognize the same small state (the Bell state) as four amplitudes, as two rules, and as two pieces joined by a link.
7. Say, for a given circuit and method, whether the method can handle it and what its size is doing as the circuit grows.
8. Explain that no method is best for every circuit, and that "how many qubits can a simulator handle?" depends on the method and on the circuit.
9. Distinguish what a simulator can show (the whole state, exact probabilities) from what a device returns (samples), and say that a simulator by default models an ideal device.
10. Explain that the size of what a method keeps is not the same as how fast it runs, and that exact and approximate answers both exist.
11. Distinguish a simulator's answer from a prediction of what a particular device will do.
12. Ask what keeps track of the work of running a circuit, whichever target runs it.

## Experience-level scope

**Beginner (V1) teaches:** that a simulator is a target that models the computation; the state-vector method and why its size doubles with each qubit; the stabilizer method and the tensor-network method conceptually (what each keeps, what it handles, what drives its cost); the Bell state three ways; three circuit families and what each method does with them; capability and growth, with the tags "computed" and "estimated"; what a simulator can show that a device cannot; ideal versus noisy named once; exact versus approximate in one paragraph.

**Intermediate (future):** the stabilizer method stated precisely, and why it is efficient; tensor networks with capped link sizes; methods that include noise; measurement and sampling in more detail.

**Advanced (future):** scaling analysis; GPU acceleration and distributed simulation; choosing among methods automatically; research-facing methods.

Do not build Intermediate or Advanced content to make V1 more complete.

**Not on this page (any level):** SDK setup, calls, or run instructions (Module 03), named simulators or products, timings and benchmarks, claims about quantum advantage or about which circuits are hard, noise models and their parameters, algorithm design, job submission and queues (05.06).

## Page structure (draft)

1. **From Targets to Simulators.** Reconnect to 05.04: a simulator is one kind of target, with a description and no calibration data. Ask 05.04's closing question ("how does it actually work out the answer, and why do different simulators behave differently?"). Answer in one sentence: a simulator is a classical program that models the computation, using one of several methods, and the method decides what it can do.

2. **The Obvious Method: Keep Every Amplitude.** The state-vector method. Show the Bell state as the four amplitudes it keeps (computed by the engine), then what happens as qubits are added: 2ⁿ amplitudes, doubling each time, with the Module 01 memory assumption stated. Connect to Module 01 and to 05.04's "limits are set by the computer". Say the wall belongs to this method.

3. **Keeping Less by Using Structure.** The same Bell state, two more ways: **two rules** it obeys (the stabilizer method) and **two small pieces joined by one link** (the tensor-network method). One short paragraph each on what the method keeps. The three forms side by side, labelled, each from its engine, with the point that they describe the same state.

4. **What Each Method Is Good For, and Where It Stops.** A compact comparison, the same four questions for each: what it keeps, what circuits it handles, what drives its cost, what it gives back. No ranking.

5. **Main Interactive: "Simulation Method Explorer."** Choose a circuit family, a number of qubits, and (for depth) a depth; read, for each method, what it keeps, whether it can handle the circuit, and how that is growing. See below.

6. **What a Simulator Can Show That a Device Cannot.** The whole state and exact probabilities, versus a device's samples; a simulator can also sample; ideal by default; noise named in one sentence (and tied to 05.04); a simulator's answer is not a prediction of a device.

7. **No Method Wins Everywhere.** The takeaway from the explorer: different circuits favour different methods; "how many qubits can a simulator handle?" has no single answer. Size is not speed. Exact versus approximate in one hedged paragraph. Pick up Module 01's caveat, with no claim about advantage.

8. **A Simulator Is a Target, Not a Forecast.** Short contrast block: simulator, device, and prediction. A simulator target needs a description (05.04) and a method (this page); neither makes its answer a forecast of a device.

9. **From Simulators to Runs.** Bridge. Show the simulator and the device as two targets, each of which will be handed work. Ask: "Whether a circuit runs on a simulator or on a device, what sends the work, waits for it, and brings the results back?" Introduce the next problem: something has to coordinate the run. Do not teach job lifecycles. End with the question and `Next: Quantum Runtime and Classical-Quantum Orchestration →`.

## Main Interactive: "Simulation Method Explorer"

- **Controls:**
  - circuit family: GHZ chain, GHZ chain with a T on every qubit, Entangling layers (each with a one-line description; the Bell circuit is the GHZ chain at two qubits);
  - number of qubits, 2 to 60 (marked at 10: "up to here, computed by running the method; beyond, estimated from the size formula");
  - depth (Entangling layers only);
  - method: State vector, Stabilizer, Tensor network (the three are shown side by side; the chosen one is marked and drives the explanation);
  - reset.
- **Display, kept in separate places:**
  - the **circuit** in words (and drawn through `QedCircuit` when it has two qubits), with a note of whether every operation is in the stabilizer method's set;
  - for each method: **what it keeps** (named), **its size** with the tag "computed" or "estimated", and **whether it can handle this circuit** (with the reason and the first operation it cannot handle when it cannot);
  - **what the size is doing**: a plain sentence per method ("doubles with each qubit", "grows slowly", "link size has grown to …");
  - a **small picture** of what the chosen method keeps (an amplitude table for up to three qubits, a list of rules, a chain of pieces with link sizes).
- **Cause, response, observation:** family, size, depth, and method are the cause; what each method keeps and whether it handles the circuit are the response; the learner's observation is which method stays small, which stops, and which grows.
- **Rules the page keeps:** the tags "computed" and "estimated" are always shown; no time, no speed, no benchmark; "cannot handle" always gives the reason; no named simulator; the tensor-network link size is the computed entanglement across the middle cut up to 10 qubits and a stated bound beyond.
- **Accessibility:** controls are real buttons and sliders; every picture has a text description; the size comparison is a real table (stacked rows on a phone); an aria-live region announces the verdict when the learner changes a choice.
- **Scope fence:** no SDK, no named simulator, no timing, no noise parameters, no claim about advantage, no job submission.

## Important pedagogical constraints (draft)

Do not imply:
- `SIMULATING QUANTUM = ALWAYS 2ⁿ`. That is one method. Others use structure.
- `A METHOD'S SIZE = ITS SPEED`. Size is not time.
- `ONE SIMULATOR HANDLES EVERY CIRCUIT OF A GIVEN SIZE`. It depends on the method and the circuit.
- `A SIMULATOR'S ANSWER = WHAT A DEVICE WILL DO`. A simulator by default models an ideal device.
- `STRUCTURE MAKES SIMULATION EASY`. It makes it easy for circuits that have that structure.
- `CLASSICAL SIMULATION IS IMPOSSIBLE BEYOND SOME NUMBER OF QUBITS`, or the reverse. The page does not say which circuits are hard.
- That a quantum computer does or does not beat any simulation method (no claim about advantage).
- That the page's size formulas are benchmarks, or that "computed" sizes describe any real simulator.
- That the three methods are the only methods, or that real simulators use exactly these descriptions.
- That a simulator can show the whole state and a device can do the same.

Do not teach here: SDK use, named simulators, timings or benchmarks, noise models, GPU or distributed simulation, algorithm design, or job submission.
