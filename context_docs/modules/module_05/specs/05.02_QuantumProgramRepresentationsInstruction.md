This section continues Module 05 — Quantum Software Stack. 05.01 introduced the responsibilities and ended by asking what a program looks like after it leaves the code we wrote. This page opens up the "describe" responsibility and shows that one computation can take several forms.
________________________________________
Goal
Teach the learner that one quantum computation can be written down in several forms, that different parts of the software stack work with different forms, and that a different form is a different description of the same computation, not a different computation.
The central progression is:
SOURCE FORM → OTHER FORMS OF THE SAME COMPUTATION → DIFFERENT RESPONSIBILITIES USE DIFFERENT FORMS → A FORM SAYS WHAT TO DO, NOT YET HOW A TARGET DOES IT
The learner should understand that a quantum program is a computation that software can describe in several ways, and that moving between those descriptions is how software hands a program from one responsibility to the next.
The key conceptual transition is:
“A quantum program is not one thing. It is a computation that software can describe in several forms, each useful for a different task.”
This section should prepare the learner for Compilation and Transpilation (05.03).
________________________________________
Learning Outcomes
By the end of the section, the learner should be able to:
	Explain that the same computation can be described in different forms.
	Recognize a circuit diagram as one representation of a program, not the program itself.
	Distinguish a source representation (what a person writes) from the forms used downstream by other software.
	Describe what each of three forms is good for and what it hides: the circuit diagram, the ordered instruction list, and the dependency graph.
	Match an operation in one form to the same operation in another form.
	Recognize which operations must happen in order and which do not, using the dependency graph.
	Explain, in plain language, why different responsibilities in the stack may need different forms.
	Explain what an intermediate representation is conceptually: a form between what you write and what a target runs.
	Distinguish a representation from a programming language, an SDK, or a quantum state.
	Recognize that two forms describing the same computation can look different, and that forms that look similar can describe different computations.
	Ask why a form that says what to compute may still need to be transformed before a particular target can run it.

Page Structure
1. What Does a Program Look Like After It Leaves the Code We Wrote?
Begin directly from the Understanding the Quantum Software Stack material.
Revisit the familiar progression:
DESCRIBE
↓
ADAPT
↓
CHECK THE TARGET
↓
COORDINATE
↓
EXECUTE
↓
RETURN RESULTS
Then ask:
“What does a quantum program look like after it leaves the code we wrote?”
Bring back the Bell-state circuit as the recurring example, drawn through QedCircuit.
Frame the page as opening up the first responsibility, describing a computation.
The learner should see a program's forms as different descriptions of one computation rather than as different programs.
Do not repeat the 05.01 architecture explorer.

2. One Computation, Several Forms
Show the Bell computation in three forms, side by side, each in a labelled card:
	Circuit diagram — the picture read left to right, drawn through QedCircuit.
	Ordered instruction list — the same operations written one per line, in an order software can process step by step.
	Dependency graph — the same operations as boxes, with an arrow from one to another when the first must happen before the second.
Name each form in one line.
State plainly that all three describe the same computation. None is “the real one” and the others copies.
Label every form as illustrative: these are teaching forms, not real file formats and not any vendor's syntax.
Do not imply that a circuit diagram is the only way to write a program.
Include a short explanation such as:
“Which one is the program?”
“All of them describe it. The program is the computation. The forms are ways of writing it down.”

3. What Each Form Is Good For, and What It Hides
Compare the three forms briefly, in a table or three short blocks.
Diagram
Easy for people to read; shows the structure at a glance. It hides the order a piece of software would process it in.
Instruction list
Easy for software to read one step at a time, and to store and pass along. It hides which order matters and which does not.
Dependency graph
Makes the ordering constraints explicit. It hides how a person would read the circuit.
Make the point that no form is better in general; each fits a task.
The learner should understand:
EACH FORM EMPHASIZES SOMETHING
↓
AND HIDES SOMETHING ELSE
Do not rank the forms, and do not describe any form as what real software always uses.

4. Main Interactive — “Representation Viewer”
Make this the primary V1 interaction.
Show the Bell computation in all three forms at once, in the labelled cards from section 2. Allow the learner to choose a form and a stage of the stack, and to select any operation.
At minimum support:
	Choosing a form (circuit diagram, instruction list, or dependency graph). The chosen form is marked as selected and drives the side panel.
	Choosing a stage: the person writing the program, transformation software, or a job sent to a target.
	Selecting one operation, such as the CNOT, from the instruction list or the dependency graph.
	Resetting the view to its starting state.
When the learner chooses a form or a stage:
	Mark the chosen form as selected, with a text label as well as a border change.
	Show a side panel that states what this form is good for, what it hides, and which responsibility from 05.01 tends to use it at this stage.
	Say that which stage uses which form is illustrative, and that real systems differ.
When the learner selects an operation:
	Highlight the same operation in every form at once, with a visible treatment and a text label such as “CNOT, step 2”.
	Show, in a text line, where the operation sits in each form: its place in the picture, its line number in the list, and which operations it must follow and precede in the graph.
Keep what the learner chooses (form, stage, operation) separate from what is derived (the three renderings and the side panel) and from what is observed (the highlighted correspondence and the text line).
The learner should visually experience:
CHOOSE A FORM, A STAGE, AND AN OPERATION
↓
SEE THE SAME COMPUTATION IN EACH FORM
↓
FIND THE SAME OPERATION EVERYWHERE
Reinforce the distinction established in 05.01:
A circuit is an instruction or description, not a physical quantum state.
Make the interaction resettable and keyboard accessible. Keep focus where it was after the view re-renders. Give the dependency graph a text equivalent, a list of “X must come before Y” statements, so no information depends on seeing the picture.
Do not add real syntax, a transformation, a compiler, or a target.

5. Source Representation and Downstream Forms
Introduce two terms in one sentence each:
	Source representation — what a person writes in a tool, shown as clearly labelled illustrative pseudo-code rather than any real SDK.
	Intermediate representation — a form between what you write and what a target runs. It is still a description of the computation.
Tie each to a responsibility from 05.01: the user program for the source form, and program representation and compilation for the intermediate forms.
Note that the backend or target description is a different kind of description: it says what a target can do, not what the program is.
Add one sentence that forms closer to the device exist, with no detail and no pointer to a page that does not exist.
The learner should understand:
WHAT A PERSON WRITES
↓
FORMS SOFTWARE PASSES BETWEEN RESPONSIBILITIES
↓
WHAT A TARGET RUNS
Do not show real OpenQASM, QIR, or any vendor syntax. Do not teach how a source form becomes an intermediate form.

6. Same Computation, or Not?
Ask:
“If the forms look so different, how do we know they describe the same computation?”
Answer conceptually: they have the same operations, on the same qubits, with the same required order and the same measurements.
Show that this works the other way too: two forms that look alike can differ in one operation and then describe different computations.
If practical, add an optional “spot the difference” check. Show two forms with one operation altered and let the learner find it and say whether the two still describe the same computation.
Keep the check informal. Do not introduce a formal definition of equivalence.
Do not imply that looking similar means being the same, or that looking different means being different.

7. A Representation Is Not a Language, an SDK, or a State
Make the distinction explicit.
Programming language or SDK
Something a person uses to produce a representation.
Representation
A description of the computation, in some form.
What the computation means
The state it prepares. This is separate again, and it is not a form of the program.
Use the Bell circuit to show that:
The diagram describes what to do; the state is what doing it produces.
Mention the meaning once, as a contrast, and do not make it a fourth form.
Do not imply that a representation is a state, a language, or a tool.

8. From Representations to Transformation
End by showing the Bell computation once more, in its three forms.
Previously:
WRITE A PROGRAM
↓
SOFTWARE DESCRIBES IT IN SEVERAL FORMS
versus:
A FORM SAYS WHAT TO COMPUTE
↓
BUT A TARGET CAN ONLY DO CERTAIN THINGS
Ask:
“If a form says what to compute, why can't a device just run it as written?”
Then introduce the next problem: targets differ in what they can do, so software has to transform forms before a target can run them.
Do not explain transformation, native operations, or connectivity here.
End with:
“If a form says what to compute, why can't a device just run it as written?”

Important Pedagogical Constraints
Do not imply:
PROGRAM = CIRCUIT DIAGRAM
Instead teach:
The diagram is one representation of a program. The program is the computation.
Do not imply:
THERE IS ONE CANONICAL FORM
Instead teach:
There is no single real form. Forms serve different tasks, and each hides something.
Do not imply:
INTERMEDIATE REPRESENTATION = MACHINE CODE OR HARDWARE INSTRUCTIONS
Instead teach:
An intermediate representation sits between what you write and what a target runs, and it is still a description of the computation.
Do not imply:
DIFFERENT FORM = DIFFERENT COMPUTATION
Instead teach:
Forms that look different can describe the same computation, and forms that look alike can describe different ones. What matters is the operations, their required order, and the measurements.
Do not imply:
REPRESENTATION = PROGRAMMING LANGUAGE, SDK, OR QUANTUM STATE
Instead teach:
A language or SDK produces a representation. A representation describes a computation. The state is what the computation prepares.
Do not imply that the illustrative forms are real file formats or any vendor's syntax.
Do not imply that every software stack uses exactly these three forms, or that a given stage always uses a given form.
Do not imply that the backend or target description is another form of the program.
Do not teach real OpenQASM or QIR syntax, serialization formats, translation rules, compiler passes, native gates, connectivity constraints, or pulse and control representations here.
Keep Beginner V1 focused on the mental model required to understand why a form must be transformed before a target can run it.

End State
The learner should leave with:
SOURCE FORM
↓
OTHER FORMS OF THE SAME COMPUTATION
↓
EACH RESPONSIBILITY USES THE FORM IT NEEDS
↓
A FORM SAYS WHAT TO COMPUTE, NOT YET HOW A TARGET DOES IT
And understand the central relationship:
Computation → several forms → the same operations found in each, with the same required order.
The central takeaway should be:
A quantum program can be described in several forms, each good for a different task. They describe the same computation, and that is why software can move a program between responsibilities.
End with:
“If a form says what to compute, why can't a device just run it as written?”
