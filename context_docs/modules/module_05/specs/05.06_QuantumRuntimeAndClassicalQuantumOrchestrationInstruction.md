## Open questions for review

Each has a recommendation. Say which you accept or change; the rest of the draft already assumes the recommendations.

1. **What is the one idea the page teaches?** The module's progression ends "…→ RUNTIME COORDINATION → RESULTS", and 05.05 ends by asking "what sends the work, waits for it, and brings the results back?". *Recommendation:* the runtime is **the coordinator around a run**, and it has four duties, taught as four verbs: **send** (turn the adapted computation into a job and hand it to a target), **track** (keep hold of the job while it waits and runs), **return** (bring back the results and make them usable), and **decide** (let the classical side choose what to run next). The first three are one job; the fourth is what turns one job into a loop. The page keeps this separate from compilation (rewrites the program), the backend description (says what a target allows), and execution (carries the run out), as 05.03 and 05.04 did.

2. **What does the main interaction show?** The taxonomy asks for an "execution lifecycle / classical–quantum coordination demonstration". *Recommendation:* a **Run Lifecycle Explorer** for **one job**, stepped by the learner. Two lanes side by side: the **program side** (the classical software that holds the program and the job) and the **target** (the simulator or the device). The learner chooses a **target** (Simulator or Device Q4, both from 05.04), a **number of shots** (for example 10, 100, 1000), and an **outcome** (the job finishes; the target rejects it at submission; the run fails partway). They press **Step** (and **Back**, **Reset**, **Run it again**). At each step the page shows the job's **status**, **what each lane holds**, and **what just crossed between them**. There is also a **Cancel** button while the job waits or runs. The hybrid loop (question 6) is an **extension of this interaction** in its own small panel, using the same model.

3. **Which lifecycle states, and how honest about their names?** *Recommendation:* a small invented set, **labelled illustrative on the page**: **Prepared → Submitted → Queued → Running → Finished**, with three exits: **Rejected** (the target refuses it at submission), **Failed** (it stops during the run, with **no results**), and **Cancelled** (the program withdrew it). **Retrieving the results is a separate action after Finished, not a state.** The page says real platforms use different names and different numbers of states, may not queue at all (a simulator running on the same computer may start at once; a shared service may queue even for a simulator), and that the page's states are a teaching model. The target description decides **rejection**: the page reuses the `allows` check from 05.03 and 05.04, so submitting the Bell circuit as first written to a target that does not allow one of its operations is rejected, and the fix is the compilation step the learner already knows. No real status strings, no vendor words.

4. **How is waiting shown without timings?** *Recommendation:* **count moments, never seconds.** Steps are numbered ("moment 4 of 8"). The device's queue is a small **invented** number of other jobs ahead ("3 jobs ahead of yours, invented"), which drops as the learner steps; the simulator's is 0 by default. The page shows **no duration, no clock, no queue length claimed to be typical, no price, no usage limit**, and says that a status such as "queued" tells you nothing about how long the wait will be. Where the page says a loop of jobs may spend most of its time waiting on a shared device, it says **may**, gives **no figure**, and does not claim it for every platform.

5. **What does "result handling" mean for a Beginner?** *Recommendation:* three steps, each shown: (a) the target returns **raw results**: for each shot, one outcome, collected as **counts** per bit string, with the shot total and the target's name (what a device returns, per 05.05); (b) the classical side **turns counts into something it can use**: a fraction (an estimate of a probability), and for the Bell circuit "how often the two bits agreed"; (c) the classical side **keeps or acts on it**: prints it, stores it, or feeds the next job. The page makes three points: **the counts are samples, not the exact probabilities** (a simulator *can* give exact ones, 05.05, but the default result for both targets is counts); **running the same job again gives different counts** (each submission is a new job); and **a finished job is not a correct answer**: Finished means the run completed, and a Failed job returns nothing at all, which is different from returning something wrong. Counts are sampled with `QedShots` (seeded: the first run is the same on every load, **Run it again** gives new counts), and **every count is labelled simulated**. The simulator path shows ideal counts (only 00 and 11 for Bell); the device path shows the same pattern with **a few other bit strings, invented and labelled so**, as 05.01 already said a device can return. No noise model, no numbers claimed to be typical.

6. **Which hybrid example, and how is algorithm design kept out?** Module 06 already runs a hybrid loop as part of VQE; Module 05 owns the software side. *Recommendation:* a **small loop** on a **one-qubit rotation**: the program sets an angle θ, sends a job with that angle, receives counts, estimates the fraction of 1s, and a **scripted, stated rule** picks the next angle, stopping when the estimate is near a stated target (target fraction 0.75, which the ideal angle of 120° reaches; start at 30°). Each pass shows a row: *angle sent → shots → counts → estimate → next angle*, in a real table (stacked rows on a phone). The learner chooses **shots per job** (for example 20, 100, 500) and the **target** (Simulator or Device Q4), and steps, runs to the end, or resets. What they observe: **every pass is a whole job** (send, track, return), so a loop of ten passes is ten jobs; **fewer shots per job give a jumpier estimate**, so the rule wanders; **more shots steady it but use more of the target**. The page shows **jobs submitted** and **shots used** as running totals, not time. The rule is called "one simple, scripted rule among many"; the page does **not** teach optimizers, gradients, cost functions, VQE, or any named algorithm, and says that algorithms which use this loop shape are taught elsewhere in the curriculum (**no cross-module links**, as the taxonomy defers them). The scripted rule moves the angle by a fixed fraction of the gap between the estimate and the target; the exact rule is fixed in the build and tested.

7. **How much of "classical–quantum feedback" does a Beginner see?** The taxonomy says "introductory classical–quantum feedback and hybrid loops", with real-time feedback listed under future depth. *Recommendation:* **two scales, one demonstrated.** (a) **Between jobs**: the loop above. (b) **Inside one run**: named in a short block only. Some circuits measure a qubit partway through and use that result to choose a later operation in the same run (the existing **Mid-Circuit Measurement** glossary entry). That happens close to the device, in the control software (05.04's boundary), too fast to go through job submission, and the page does not demonstrate it. Real-time feedback, latency, and resource management are Advanced. The page also says plainly that a hybrid loop does **not** make the quantum side "in charge": the classical side sets the angle, sends the job, reads the results, and decides what happens next.

8. **Which responsibilities does the page name for "the program side"?** *Recommendation:* the page is about **who holds what**, so the lanes list, in plain words and the same neutral treatment as 05.01: on the program side, **the program (as a list of instructions, the "job form" 05.02 promised), the job's settings (target, shots), the job's number and status, and the returned counts**; on the target side, **the description of what it allows (05.04), the method or device that carries out the run (05.05 for a simulator), and the counts it hands back**. The job's payload is shown with `QedProgramForms.instructionListHTML` (the instruction-list form of the adapted circuit from 05.02 and 05.03), so the learner sees that a job carries a computation in a form a target can read, not a drawing.

9. **What is the page's recurring example, and where is it extended?** *Recommendation:* the **Bell circuit with 100 shots** carries the lifecycle explorer; the **one-qubit rotation** carries the loop. Say once that the rotation is used because Bell has no parameter to change between runs, and record that in `llm/FLAGS.md`. The rotation reuses `QedGates`' rotation matrices, as Module 02.04 does.

10. **Where does the code live?** *Recommendation:* a **new pure module `QedRuntime` (`runtime.js`)**: the lifecycle as data (`STATES`, allowed transitions, who holds what in each state), `newJob(circuit, target, shots, options)`, `advance(job)` / `cancel(job)` (a small state machine that returns a new job and never mutates), `timeline(job, outcome)` (the ordered moments for a chosen outcome), `check(job)` (rejection from the target's `allows`, using `QedTransform.adapt(...).problems`), `results(job)` (seeded counts through `QedShots`, plus the invented off-pattern counts for the device path), `summarize(counts)` (fractions, the agreement rate), `loop` helpers (`rotationProbability(θ)`, `nextAngle(estimate, angle, target)`, `runLoop(options)` returning the table rows and running totals), and small renderers (a two-lane lifecycle view, a counts table, the loop table). It calls `QedShots`, `QedGates`, and `QedTransform` at run time, and reads the `SIMULATOR` and `DEVICE` descriptions from `QedBackend` (tested with `loadModules`). Page-local: the explorer and loop wiring, the contrast wording, and the checks. 05.07 reuses the whole module for the full workflows.

11. **Experience levels.** *Recommendation:* as on 05.02 to 05.05, **V1 is Beginner-only, with no gated blocks.** Intermediate (future): the fields of a job and a result object, errors and retrying, running several jobs together, binding parameters to a circuit before sending, waiting versus checking back later in code. ## Goal

Teach the learner that a quantum program does not run itself: a coordinating layer turns the adapted computation into a job, hands it to a target, keeps track of it, brings the results back in a form software can use, and lets the classical side decide what to run next, and that a loop of such jobs is how classical and quantum work are combined.

Central progression:

`AN ADAPTED PROGRAM → A JOB SENT TO A TARGET → TRACKED WHILE IT WAITS AND RUNS → RESULTS RETURNED AS COUNTS → CLASSICAL PROCESSING → THE NEXT JOB`

Key conceptual transition: **"Running a circuit is not one step. A job is sent, tracked, and returned, and the classical side can use what comes back to decide what to send next."**

It opens by answering the question 05.05 ended on ("what sends the work, waits for it, and brings the results back?") and ends by asking the question that motivates 05.07.

## Learning outcomes (Beginner)

The learner should be able to:

1. Explain that the runtime is the coordinator around a run, and name its four duties: send, track, return, and decide.
2. Describe a job as a computation in a form a target can read, together with its settings, sent to a target and tracked.
3. Describe the stages of a job's life in plain words, and say that real platforms name and number them differently.
4. Distinguish submitting a job from finishing it, and a finished job from a correct answer.
5. Explain that a job can be rejected before it runs and can fail while running, and that a failure returns no results.
6. Describe what comes back from a run: counts of outcomes over the shots, and say they are samples that differ from run to run.
7. Describe result handling: counts become numbers the classical side can use, and those numbers are kept or acted on.
8. Say what each side holds at each stage (the program side and the target).
9. Describe a hybrid loop: results from one job help the classical side choose the next job.
10. Say that every pass of a loop is a whole job, and what changes with fewer or more shots per job.
11. Distinguish feedback between jobs from feedback inside a single run, and say that the second is handled close to the device.
12. Distinguish the runtime from compilation, from a backend description, and from execution, and say that a status says nothing about how long a wait will be.
13. Ask what changes and what stays the same when all the responsibilities work together on one computation.

## Experience-level scope

**Beginner (V1) teaches:** the runtime's four duties; a job and its lifecycle (as an illustrative model); who holds what on each side; rejection, failure, and cancelling; counts as the returned result; turning counts into numbers; the hybrid loop between jobs with a small worked loop; feedback inside a run named once; no timings anywhere.

**Intermediate (future):** the fields of a job and a result in detail; errors and retrying; running several jobs together; binding parameters to a circuit before sending; waiting versus checking back later.

**Advanced (future):** real-time classical feedback; hybrid execution patterns; distributed runtimes; scheduling and fairness; latency and resource management.

Do not build Intermediate or Advanced content to make V1 more complete.

**Not on this page (any level):** SDK calls, polling code, or run instructions (Module 03); named services, platforms, or products; real status names, queue lengths, durations, pricing, or usage limits; algorithm design, optimizers, or VQE (Module 06); error correction and decoding (Module 07); calibration physics or control electronics; noise models and their parameters.

## Page structure (draft)

1. **From Targets to Runs.** Reconnect to 05.05: a simulator and a device are two targets, each with a description, and each will be handed work. Ask 05.05's closing question. Answer in one sentence: a runtime sends the work, tracks it, brings results back, and lets the classical side decide what comes next. Bring back the Bell circuit.

2. **A Job: The Work in a Form a Target Can Read.** What the runtime sends. A job is the adapted computation (the instruction-list form from 05.02, the result of 05.03) plus settings (the target and the number of shots), with a number so it can be tracked. Show the Bell job's payload through `QedProgramForms.instructionListHTML`. Say the job is not a drawing of the circuit and not the compiled circuit alone.

3. **A Job's Life.** The illustrative lifecycle: prepared, submitted, queued, running, finished, with the three exits. Say that real platforms differ, that a simulator may not queue, and that a status says nothing about how long a wait will be. Introduce the two lanes: the program side and the target. Introduce the word **moment**.

4. **Main Interactive: "Run Lifecycle Explorer."** See below.

5. **Results: From Counts to Numbers.** What comes back and what the classical side does with it. Counts per bit string; samples differ from run to run (run it again); counts turned into a fraction or an agreement rate; kept or acted on. A finished job is not a correct answer; a failed job returns nothing. A simulator can also give exact probabilities (05.05), but the default result for both targets is counts.

6. **When the Next Job Depends on the Last: Hybrid Loops.** Extend the interaction: a small loop on a one-qubit rotation. The program sets an angle, sends a job, receives counts, estimates a fraction, and a scripted rule sets the next angle. Every pass is a whole job. Fewer shots per job give a jumpier estimate; more shots steady it and use more of the target. Running totals: jobs submitted and shots used. A hybrid loop is a pattern, not an algorithm; algorithms that use it are taught elsewhere.

7. **Feedback Between Jobs and Inside a Run.** A short contrast block. Between jobs: the loop, through submission and results. Inside a run: a measurement partway through a circuit can decide a later operation in the same run (Mid-Circuit Measurement), handled close to the device, too fast for job submission, and not demonstrated here. Real-time feedback is Advanced.

8. **The Runtime Is Not the Compiler, the Backend, or the Run.** A short contrast block, extending 05.03's: compilation rewrites the program; the backend description says what a target allows; the runtime coordinates; execution carries the run out. Use the lifecycle to show where each acts (compilation before the job, the description when the target decides on rejection, the runtime throughout, execution while running).

9. **From Responsibilities to Workflows.** Bridge. Previously: each responsibility on its own. Now: all of them on one computation, on a simulator and on a device. Ask: "You have met every responsibility one at a time. When all of them work on one computation, on a simulator and on a device, what stays the same, and what changes?" Introduce the next problem: put it all together. Do not teach the full workflows here. End with the question and `Next: Integrated Quantum Software Workflows →`.

## Main Interactive: "Run Lifecycle Explorer"

- **Controls (what the learner changes):**
  - target: Simulator or Device Q4 (both synthetic, from 05.04);
  - shots: for example 10, 100, 1000;
  - outcome: the job finishes; the target rejects it at submission (the Bell circuit sent with an operation the target does not allow); the run fails partway;
  - Step, Back, Cancel (while the job waits or runs), Run it again (a new job with a new number and new counts), Reset.
- **Display, kept in three separate places:**
  - **the lanes** (derived): the program side and the target, each listing what it holds at this moment, with the item that just crossed between them marked;
  - **the status** (derived): the current state, its glyph and label, the moment number, and (device) the invented number of jobs ahead;
  - **the result** (observed): after Finished, the counts per bit string, the shot total, the target's name, and a plain sentence ("These are samples. Running the job again gives different counts."); after Rejected or Failed, "no results" and the reason in words.
- **Cause, response, observation:** target, shots, outcome, and the learner's steps are the cause; the lanes and status are the response; what comes back (or that nothing does) is the observation.
- **Rules the page keeps:** every status, count, and job number is labelled invented or simulated; no clock, no duration, no real queue length, no vendor words; "Finished" never implies "correct"; a rejected or failed job states that there are no results and why.
- **Accessibility:** controls are real buttons and selects; the lifecycle has a text description and an ordered list alternative; an aria-live region announces each step's status and what crossed; focus stays where it was after a re-render; the counts are a real table (stacked rows on a phone).
- **Scope fence:** no SDK, no polling code, no named platform, no timing, no pricing, no noise model.

### Checks

- *Prediction task:* "You submit a job and its status is Queued. What does that tell you about how long the wait will be?" (nothing); then compare with the explorer.
- *Conceptual question:* "A job's status is Finished. Does that mean the answer is correct?" with feedback on each wrong choice (it means the run completed; whether the results are useful depends on the program, the target, and how they are interpreted).
- *Transfer task:* "A job is Failed. What results come back?" (none, which is different from results that are wrong), and then "what would you do next?" (decide whether to resubmit, change the job, or choose another target).

## The hybrid-loop panel (extension of the interaction)

- **Controls:** target (Simulator or Device Q4), shots per job (for example 20, 100, 500), Step, Run to the end, Reset.
- **Display:** a table with one row per pass: angle sent, shots, counts of 0 and 1, estimate of the fraction of 1s, next angle; running totals for jobs submitted and shots used; the stated target fraction (0.75) and the rule in words.
- **Observed:** each row is a whole job; with 20 shots the estimates jump and the angle wanders; with 500 it settles with fewer surprises and uses more shots; the total number of jobs is what a loop costs the runtime.
- **Rules the page keeps:** the rule is scripted and stated, and called one among many; no optimizer, gradient, or cost function; no claim that a loop is better than anything; seeded counts so the first run repeats.

## Important pedagogical constraints (draft)

Do not imply:
- `SUBMITTED = FINISHED`. Submitting hands the work over; the run happens later.
- `FINISHED = CORRECT`. It means the run completed.
- `A STATUS = A TIME ESTIMATE`. "Queued" says nothing about how long a wait will be.
- `A FAILED JOB = A WRONG ANSWER`. A failed job returns nothing.
- `COUNTS = THE EXACT PROBABILITIES`. They are samples and differ from run to run.
- `THE PAGE'S STATES = THE STATES OF ANY REAL PLATFORM`. They are an illustrative model; real platforms name and number them differently and may not queue.
- `THE RUNTIME = THE COMPILER, THE BACKEND, OR THE RUN`.
- `HYBRID = THE QUANTUM SIDE IS IN CHARGE`. The classical side decides what is sent next.
- `A HYBRID LOOP = AN ALGORITHM`, or `A LOOP IS BETTER THAN SOMETHING ELSE`. It is a pattern; make no claim about advantage.
- That feedback always happens between jobs. Some happens inside a run, close to the device.
- That every platform has a queue, or that waiting dominates every loop.

Do not teach here: SDK use, polling code, named platforms, real statuses or timings, pricing, algorithm design or optimizers, error correction, calibration physics, or noise models.
