This section continues Module 05 — Quantum Software Stack. 05.02 showed that one computation has several forms and ended by asking why a device cannot just run a form as written. This page answers that question and opens up the "adapt" responsibility from 05.01.
________________________________________
Goal
Teach the learner that software transforms a program so a particular target can run it, that a valid transformation changes the form and not the meaning, and that adapting a program has a cost that software can sometimes reduce.
The central progression is:
A FORM SAYS WHAT TO COMPUTE → A TARGET ALLOWS ONLY SOME OPERATIONS → SOFTWARE REWRITES THE PROGRAM FOR THE TARGET → THE MEANING IS KEPT → ADAPTING HAS A COST, AND SOMETIMES IT CAN BE REDUCED
The learner should understand that a program as written may not be a program a target can run, and that software rewrites it into a form the target allows.
The key conceptual transition is:
“A program as written may not be a program a target can run. Software rewrites it into a form the target allows, keeping what it computes, and that rewrite can cost extra operations.”
This section should prepare the learner for Hardware Abstraction and Backend Capabilities (05.04).
________________________________________
Learning Outcomes
By the end of the section, the learner should be able to:
	Explain that a program may need to be transformed before a particular target can run it.
	Distinguish compilation (turning a program into something a target can run) from transpilation (a circuit-to-circuit rewrite), and say that tools use these words differently.
	Give two kinds of limit a target can have: the operations it allows, and which way a two-qubit operation may point.
	Explain that the limits belong to the target, so the same program may need different rewrites for different targets.
	Describe a valid transformation as one that changes the form and keeps the meaning.
	Recognize, in the explorer, a gate rewritten as a sequence of other gates, and a CNOT turned round.
	Explain that adapting a program can add operations, and compare how many operations each target needs.
	Explain that a rewrite can sometimes shorten a circuit without changing what it does, by cancelling a pair that undoes itself.
	Explain that fewer operations is not the only goal, and that what is best depends on the target.
	Distinguish compilation from running a program, from describing a target, and from runtime coordination.
	Ask where a target's description of what it allows comes from, and whether it can change.

Page Structure
1. From Forms to Transformation
Begin directly from the Quantum Program Representations material.
Revisit the familiar progression:
THE BELL COMPUTATION
↓
SEVERAL FORMS OF IT
↓
A FORM SAYS WHAT TO COMPUTE
Then ask:
“If a form says what to compute, why can't a device just run it as written?”
Answer in one sentence: because a target allows only some operations.
Bring back the Bell circuit, drawn through QedCircuit, as the recurring example.
Frame the page as opening up the second responsibility from 05.01, adapting a program.
The learner should see transformation as software rewriting a form, not as running the program or changing what it computes.
Do not repeat the 05.01 architecture explorer or the 05.02 viewer.

2. Same Meaning, Different Form
Introduce the idea of a transformation with one small rewrite, shown as a before and an after.
Show the Bell circuit and a rewritten version side by side, with the state's name unchanged under both: “the Bell state; 00 and 11, half each.”
Introduce two terms in one sentence each:
	Compilation — the responsibility of turning a program into something a target can run.
	Transpilation — a circuit-to-circuit rewrite that keeps the circuit's meaning.
State plainly that tools use these two words in different ways, and that this page does not claim how any particular tool uses them.
Include a short explanation such as:
“Did the rewrite change what the program computes?”
“No. It changed the form. The state it prepares is the same.”
Do not imply that compilation means running the program.

3. Why a Target Cannot Always Run It As Written
Introduce two kinds of limit, one after the other, each shown on the Bell circuit and each a limit of a target, not of the program.
Clearly distinguish:
	The operations a target allows — a target with no H cannot run the Bell circuit as written.
	Which way a two-qubit operation may point — a target may allow a CNOT from q₁ to q₀ and not from q₀ to q₁.
Add one sentence that larger devices do not connect every pair of qubits, with nothing more. Do not show routing.
Say that each target on this page is a small given description, and that where such a description comes from is the next page's subject.
Label the targets as invented for this page: not real devices, and not any vendor's.
The learner should understand:
THE PROGRAM SAYS WHAT TO DO
↓
THE TARGET ALLOWS ONLY SOME OPERATIONS
↓
THE PROGRAM MAY NEED REWRITING
Do not imply that the limits are properties of the program.

4. Main Interactive — “Transformation Explorer”
Make this the primary V1 interaction.
Allow the learner to choose a target and to decide whether to cancel pairs that undo themselves.
At minimum support:
	Choosing a target: Open, One-way CNOT, or Rotations, each with a one-line description of what it allows.
	A toggle, “Cancel pairs that undo themselves”.
	Resetting the view to its starting state.
When the learner chooses a target:
	Show the target: its name, the operations it allows, and which two-qubit directions it allows, labelled “invented for this page”.
	Show the original circuit and the adapted circuit, each drawn through QedCircuit and each listed through QedProgramForms, in cards labelled “Original” and “Adapted for this target”.
	Mark the operations the rewrite added or removed with a text tag (“added”, “removed”) and an outline, using the highlight from 05.02.
	Show the steps taken, in words, and name the limit that caused each one. For example: “Replaced CNOT q₀→q₁ with H, H, CNOT q₁→q₀, H, H, because this target only allows the CNOT from q₁ to q₀.”
	Show the counts: operations and two-qubit operations before and after. Show measurements separately; they are the same in both.
	Show the check: the name of the state and the joint outcome bars, before and after.
When the learner turns on the toggle:
	Cancel only a pair that undoes itself, on one qubit, with nothing between them.
	Show the cancelled pair as “removed”, and say how many operations it saved.
For the Open target, change nothing and say so.
Keep what the learner chooses (target, toggle) separate from what is derived (the adapted circuit and its steps) and from what is observed (the counts and the check).
The learner should visually experience:
CHOOSE A TARGET
↓
SEE THE PROGRAM REWRITTEN FOR IT
↓
SEE THE MEANING KEPT AND THE COST COUNTED
Reinforce the distinction established in 05.01 and 05.02:
Compilation rewrites a program. Running it is a separate responsibility.
Make the interaction resettable and keyboard accessible. Give each circuit a text description and an instruction list. Give the steps and counts as text. Announce a change of target and the check result in an aria-live region. Keep focus where it was after the view re-renders.
Include these checks:
	Prediction task: “A target has no H. Before the explorer shows it, how many operations will the Bell circuit need there?” Offer a few options, then compare with the explorer (4: three turns and the CNOT).
	Conceptual question: “A circuit is rewritten for a target. What must stay the same?” The answer is what it computes. Give feedback on each wrong choice, including that the number of operations may change and that the form always changes.
	Transfer task: follow the steps for the One-way CNOT target, then say why cancelling saved two operations.
Do not add a real device, an SDK, a target format, calibration data, routing, a third qubit, or pulses.

5. What Adapting Costs
Show a table, computed from the same model as the explorer, that sets the three targets side by side:
	operations before adapting
	operations after adapting
	operations after cancelling pairs
	two-qubit operations
Derive every number from QedTransform. Do not type any number into the page.
The learner should discover that:
	The Open target needs nothing.
	The One-way CNOT target goes from 2 to 6 operations, and back to 4 after cancelling.
	The Rotations target goes from 2 to 4.
	The One-way CNOT target keeps one two-qubit operation throughout.
State that adapting costs operations, and that cancelling pairs can win some back.
Ask:
“Which target needed the most extra operations?”
Do not claim that any operation costs more or is noisier on a real device. Say only that on a real device some operations may cost more than others, and that the next page says how software learns it.

6. A Valid Transformation Keeps the Meaning
Revisit the check from the explorer.
Explain that a valid rewrite changes the form and not what the program computes, and that real tools rely on rewrite rules known to be valid.
Say plainly that the check on this page is a demonstration: it shows the state's name and the outcomes before and after, and it is not how real tools know a rewrite is valid.
Contrast it with changing the computation: replace H by X in the rewrite and show that the state's name changes.
Add one sentence that some tools also make approximate changes, with no detail.
Do not introduce amplitudes or global phase at Beginner. Amplitude-level equivalence is Intermediate.
Do not use the 05.02 same-computation comparison here. It compares the operations written on each qubit, so it would call any transformed circuit different.

7. Fewer Operations Is Not the Only Goal
Make the tradeoff explicit in a short block.
Fewer operations, fewer two-qubit operations, and a shorter circuit are different goals.
Which one matters depends on the target.
Trying harder to optimize also takes time.
The learner should understand:
A SHORTER CIRCUIT
↓
IS NOT AUTOMATICALLY THE BEST ONE FOR EVERY TARGET
Count operations and two-qubit operations only. Do not introduce depth or scheduling.
Do not claim that any operation is noisier on a real device.

8. Compilation Is Not Execution, a Backend, or a Runtime
Make the distinction explicit, using the responsibilities from 05.01.
Compilation
Rewrites the program so a target can run it.
Backend or target description
Says what a target allows. It is not another form of the program.
Runtime
Coordinates a run.
Execution
Carries the run out.
Use the explorer to show that:
The rewrite is not the run, and the target's list is not the rewrite.
Do not imply that these words are interchangeable.

9. From Transformation to Targets
End by showing the three targets once more, each with its list of what it allows.
Previously:
A FORM SAYS WHAT TO COMPUTE
↓
SOFTWARE REWRITES IT FOR A TARGET
versus:
THE REWRITE DEPENDS ON THE TARGET'S LIST
↓
BUT WHERE DOES THAT LIST COME FROM?
Ask:
“Where does a target's list of what it allows come from, and could it change?”
Then introduce the next problem: software needs a description of each target, and a device is tuned over time.
Do not teach target descriptions, calibration, or any device property here.
End with:
“Where does a target's list of what it allows come from, and could it change?”

Important Pedagogical Constraints
Do not imply:
COMPILATION = RUNNING THE PROGRAM
Instead teach:
Compilation rewrites a program. Execution carries it out.
Do not imply:
A TRANSFORMATION CHANGES WHAT THE PROGRAM COMPUTES
Instead teach:
A valid transformation changes only the form. The meaning is kept.
Do not imply:
THERE IS ONE RIGHT COMPILED FORM
Instead teach:
Different targets, and different goals, give different forms.
Do not imply:
FEWER OPERATIONS IS ALWAYS BETTER, OR MORE OPERATIONS IS ALWAYS WORSE
Instead teach:
Which is best depends on the target and on the goal.
Do not imply:
THE COMPILED CIRCUIT IS THE REAL PROGRAM
Instead teach:
It is another form of the same computation.
Do not imply that every target needs the same rewrite. The limits belong to the target.
Do not imply that the three targets are real devices, or that the limits shown are any vendor's.
Do not imply that compilation, a backend description, and a runtime are the same thing.
Do not imply that the check on this page is how real tools know a rewrite is valid.
Do not claim that any operation is noisier or costlier on a real device.
Do not teach how a target's description is made or shaped, calibration or device properties, noise, routing or mapping algorithms, scheduling, depth, real SDK or compiler behavior, or any optimization algorithm here.
Keep Beginner V1 focused on the mental model required to understand why software needs a description of each target.

↓
SOFTWARE REWRITES FOR THE TARGET, KEEPING THE MEANING

ADAPTING COSTS OPERATIONS, AND SOMETIMES SOME CAN BE WON BACK

Program → target's limits → rewrite → same meaning, different form, counted cost.

Software rewrites a program so a particular target can run it. A valid rewrite changes the form and keeps the meaning, it can cost extra operations, and different targets need different rewrites.
