## Open questions for review

1. **Real syntax or illustrative forms?** Taxonomy V1.1 lists OpenQASM, QIR and IR design as Intermediate/Advanced. *Recommendation:* no real syntax at Beginner. Show clearly labelled "illustrative" forms only, so the page teaches the idea and stays vendor-neutral (Vision §17).
2. **Which forms to show?** *Recommendation:* three: (a) circuit diagram, (b) ordered instruction list, (c) dependency graph (which operations must come before which). 3. **Exclude "what the circuit means" (the state it prepares) from the forms.** Mixing meaning with representation risks the "circuit = quantum state" misconception that 05.01 guarded against. *Recommendation:* mention once as a contrast, do not make it a form.
4. **Device-level forms (pulses, control signals).** Taxonomy defers pulse-level interfaces to Advanced. *Recommendation:* one sentence acknowledging that forms closer to the device exist, with no detail and no pointer to a page that doesn't exist.
5. **Shared components.** *Recommendation:* reuse `QedCircuit` (extend it to accept operation IDs and a highlighted set) and `QedSoftwareStack` (the responsibility definitions); create one new module, `QedProgramForms`, holding the Bell computation as operations with IDs and rendering the instruction list and dependency graph. 05.03 will reuse it to show transformed forms. *Question:* extend `QedCircuit` or keep it untouched and highlight in the new module?
6. **Glossary.** Likely new entries: *Intermediate Representation*, *Program Representation* (or one combined entry with the alias), *Dependency Graph*? 7. **An optional "spot the difference" check** (two forms, one operation altered, learner finds the mismatch) would teach "same computation or not?" without any formal equivalence. *Recommendation:* include as optional if practical; cut if the page gets heavy.

## Goal

Teach the learner that one quantum computation can be written down in several different forms, that different parts of the software stack work with different forms, and that a different form is a different description of the *same* computation, not a different computation.

Central progression:

`SOURCE FORM → OTHER FORMS OF THE SAME COMPUTATION → DIFFERENT RESPONSIBILITIES USE DIFFERENT FORMS → A FORM SAYS WHAT TO DO, NOT YET HOW A TARGET DOES IT`

Key conceptual transition: **"A quantum program is not one thing. It is a computation that software can describe in several forms, each useful for a different job."**

It opens by answering the question 05.01 ended on ("What does a quantum program look like after it leaves the code we wrote?") and ends by asking the question that motivates 05.03 ("if a form says what to compute, why can't a device just run it as written?").

## Learning outcomes (Beginner)

The learner should be able to:

1. Explain that the same computation can be described in different forms.
2. Recognize a circuit diagram as one representation of a program, not the program itself.
3. Distinguish a source representation (what a person writes) from forms used downstream by other software.
4. Describe what each of three forms is good for and what it hides: diagram, instruction list, dependency graph.
5. Match an operation in one form to the same operation in another form.
6. Recognize which operations must happen in order and which do not (using the dependency view).
7. Explain, in plain language, why different responsibilities in the stack may need different forms.
8. Explain what an "intermediate" representation is conceptually: a form between what you write and what a target runs.
9. Distinguish a representation from a programming language, an SDK, or a quantum state.
10. Recognize that two forms describing the same computation can differ while two forms that look similar can describe different computations.
11. Ask why a form that says *what* to compute may still need to be transformed before a particular target can run it.

## Experience-level scope

**Beginner (V1) teaches:** the Bell circuit in three illustrative forms; source versus downstream forms; what each form is good for and hides; correspondence between forms; "intermediate" as a conceptual middle form; representation ≠ language/SDK/state.

**Intermediate (future):** OpenQASM and QIR-style forms as real examples; how a circuit becomes an IR in practice; metadata and parameters in representations; multi-circuit and classical-control representations; comparison across two SDK workflows.

**Advanced (future):** IR design and invariants; transformation-friendly representations; versioning and interchange formats; device-level (pulse) representations.

Do not build Intermediate or Advanced content to make V1 more complete.

## Page structure (draft)

1. **What Does a Program Look Like After It Leaves the Code We Wrote?** Reconnect to the 05.01 journey (describe → adapt → check target → coordinate → execute → return) and its closing question. Introduce the Bell circuit again as the recurring example. Frame: "describe" is the responsibility we now open up.

2. **One Computation, Several Forms.** Show the Bell computation as: (a) circuit diagram, (b) ordered instruction list, (c) dependency graph. Name each form in one line. State plainly: all three describe the same computation. Not "the real one" and "the copies".

3. **What Each Form Is Good For, and What It Hides.** Short comparison. Diagram: easy for people to read, shows structure at a glance. Instruction list: easy for software to process one step at a time and to store. Dependency graph: makes ordering constraints explicit. Each hides something (the diagram hides the order software processes it in; the list hides which order matters; the graph hides how a person reads it). No form is better in general.

4. **Main Interactive: "Representation Viewer".** Learner picks a form and a stage of the stack (the person writing it, transformation software, a job sent to a target). The same Bell computation is shown in the chosen form. Learner selects one operation (for example the CNOT) and sees it highlighted in every form at once. A side panel states what this form is good for, what it hides, and which responsibility from 05.01 tends to use it. Cause (choice of form and stage) is separate from what is derived (the rendering) and observed (the highlighted correspondence). Resettable, keyboard-accessible, text equivalents for every highlight.

5. **Source Representation vs. Downstream Forms.** Introduce *source representation* (what a person writes in a tool; shown as clearly labelled illustrative pseudo-code, not a specific SDK) and *intermediate representation* (a form between what you write and what a target runs). Tie each to a 05.01 responsibility. Note that the backend/target description is a different kind of description (what a target can do), not another form of the program. One sentence: forms closer to the device exist; not covered here.

6. **Same Computation, or Not?** Ask: "If forms look so different, how do we know they describe the same computation?" Answer conceptually: same operations, same required order, same measurements. Optional "spot the difference" check: two forms with one altered operation; learner finds it and says whether it is still the same computation.

7. **A Representation Is Not a Language, an SDK, or a State.** Contrast block. A programming language or SDK is something a person uses to produce a representation. A representation is a description of a computation. What the computation *means* (the state it prepares) is separate again and is not a form of the program.

8. **From Representations to Transformation.** Show the Bell computation once more and ask: "If a form says what to compute, why can't a device just run it as written?" Introduce the next problem: targets differ in what they can do, so software transforms forms. Do not teach transformation here. End with the question and `Next: Compilation and Transpilation →`.

## Important pedagogical constraints (draft)

Do not imply:
- `PROGRAM = CIRCUIT DIAGRAM` — the diagram is one representation.
- `ONE CANONICAL FORM` — there is no single "real" form; forms serve different jobs.
- `INTERMEDIATE REPRESENTATION = MACHINE CODE OR HARDWARE INSTRUCTIONS` — it sits between source and target and is still a description of the computation.
- `DIFFERENT FORM = DIFFERENT COMPUTATION` — and the reverse: similar-looking forms are not automatically the same.
- `REPRESENTATION = PROGRAMMING LANGUAGE / SDK` or `REPRESENTATION = QUANTUM STATE`.
- That the illustrative forms are real file formats or any vendor's syntax.

Do not teach here: real OpenQASM/QIR syntax, serialization formats, translation rules, compiler passes, native gates, connectivity constraints, pulse or control representations. Those belong to later pages or later depth.

## End state (draft)

The learner leaves with: `SOURCE FORM → OTHER FORMS OF THE SAME COMPUTATION → EACH RESPONSIBILITY USES THE FORM IT NEEDS → A FORM SAYS WHAT TO COMPUTE, NOT YET HOW A TARGET DOES IT`.

Takeaway: *A quantum program can be described in several forms, each good for a different job. They describe the same computation, and that is why software can move a program between responsibilities.*

Ends with: "If a form says what to compute, why can't a device just run it as written?" and **Next: Compilation and Transpilation →**
