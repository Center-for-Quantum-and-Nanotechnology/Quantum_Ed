## Open questions for review

Each has a recommendation. Say which you accept or change; the rest of the draft already assumes the recommendations.

1. **What is the one idea, given that 05.01 already walked both paths?** *Recommendation:* 05.01 introduced the responsibilities as labels with fixed illustrative text. This page **composes the built models into one run** and adds **arrangement**. Every step shows an artifact that a shared module really produced: the instruction list (`QedProgramForms`), what the target allows (`QedBackend`), the adapted circuit (`QedTransform`), the job and its lifecycle (`QedRuntime`), the method on the simulator path (`QedSimMethods`), and the counts. The new teaching content is (a) a computed comparison of what stays the same and what changes between the two paths, and (b) three **arrangements** of the same steps. The page does not re-teach any responsibility; each step links back to its page.

2. **What does the main interaction show?** The taxonomy asks for an "end-to-end workflow explorer with alternative target paths". *Recommendation:* a **Workflow Explorer** for the Bell circuit. The learner chooses a **target path** (Simulator or Device Q4), an **arrangement** (three, question 3), and, on the device path only, whether **a newer report arrives while the job waits** (No or Yes). They step through the workflow (Step, Back, Reset). At each step the page shows the **responsibility** (with its group: Application Layer, where they meet, execution target, Control Layer), **who performs it** in this arrangement, **what it received**, **what it produced**, and, for the steps that decide something, **what it knew when it acted**. The steps are: write the program; describe it as data; (device only) the device's software reports its condition; check what the target allows; adapt the program; send the job; run it; return the counts; interpret them. That is **nine steps on the device path and eight on the simulator path**.

3. **Which arrangements?** Core Learning Contract item 9 says responsibilities "can be combined, distributed, or ordered differently". *Recommendation:* **three, invented and labelled illustrative, with no vendors or products named**:
   - **Prepare, then send.** Your tools describe the program, check the target, and adapt it, then send a job that already carries the adapted form (the 05.06 workflow).
   - **Send, then the service prepares.** Your tools send the program as written. The service checks the target and adapts it after receiving the job and after any wait.
   - **One tool does it all.** One call performs every step. The steps still happen in the same order as in the first arrangement, but they are combined into one visible action, with a "what happened inside" list that can be opened.
   Say that these are three examples, not a complete list, and that no platform is claimed to work this way. The learner should see **combined is not removed**: the one-tool arrangement hides the steps, it does not delete them.

4. **How does the Control Layer show up, and how far does the page go?** The taxonomy says information flows both ways, that a device report **may** inform the backend description and compilation, and that this is "not automatic". *Recommendation:* on the device path, the **report** step produces the calibration snapshot description from 05.04 (a time, a status, and the reported values for the two connected pairs the page uses). The **check** and **adapt** steps then show what they knew. To make "possible, policy-dependent" concrete without teaching routing, the adapt step shows **which connected pair a stated policy would choose** (`QedBackend.choosePair`, policy "lowest two-qubit error"), from the report that step has. In the data this really differs: the earlier report picks Q1–Q2 and the later report picks Q0–Q1. With **Prepare, then send** the step uses the report available at preparation (the earlier one). With **Send, then the service prepares**, it uses the report available after the wait, which is the later one **only if** the learner chose "a newer report arrives while the job waits: Yes". With **One tool**, it behaves as Prepare, then send. The page says plainly that **this is a possible decision**, that **placement and routing are not taught here** (Intermediate), that **the chosen pair is shown but not applied to the circuit**, and that **the page does not model how the choice would change the counts**. If you would rather cut this and show the Control Layer only as a labelled step, say so; it is the part with the most explanatory weight and the most risk of implying that telemetry controls results.

5. **How much new code, and where does it live?** *Recommendation:* a **new pure module `QedWorkflow` (`workflow.js`)** that composes the built models and adds nothing physical:

   - `validate(build)`, which checks the constraints and that every step appears exactly once;
   - small renderers (the step list, the comparison table, the arrangement table).
   Page-local: the explorer wiring, the contrast wording, the checks, and the module recap. **Tests** (`tests/js/workflow.test.js`, with `loadModules`): every arrangement satisfies every ordering constraint on both paths; each step appears exactly once; the device path has nine steps and the simulator path eight; the counts are the same in all three arrangements for the same job; the adapted program is the same in the arrangements that adapt, and the job payload differs where the arrangements differ (adapted form versus as written); `compare` of the two paths reports exactly the responsibilities whose artifacts differ and none of the others; the chosen pair follows the stated report and policy; the "newer report" switch changes the pair only in the arrangement that waits before preparing; inputs are left unchanged; and a seeded cross-check that the whole `build` agrees with calling each model by hand. ## Goal

Teach the learner to follow one computation through every software responsibility on a simulator path and on a device path, to see what stays the same and what changes between them, and to recognize that the same responsibilities can be ordered, combined, and placed differently, so that what each step knows depends on when it acts.

Central progression:

`ONE COMPUTATION → THE SAME RESPONSIBILITIES AT WORK → A SIMULATOR PATH AND A DEVICE PATH → DIFFERENT ARRANGEMENTS OF THE SAME RESPONSIBILITIES → NO ONE UNIVERSAL ORDER`

Key conceptual transition: **"A software stack is not a fixed pipeline. It is a set of responsibilities, and different platforms arrange them differently, combine them, and decide when each one acts and what it knows."**

It opens by answering the question 05.06 ended on ("what stays the same, and what changes?") and closes the module with a recap and a question that points outward.

## Learning outcomes (Beginner)

The learner should be able to:

1. Trace one computation through the whole workflow, naming each responsibility and what it passes on.
2. Say which responsibilities are the same on a simulator path and on a device path, and which differ.
3. Explain what the device path adds: its software reports its condition, which may inform the description of the target.
4. Distinguish Application Layer responsibilities from Control Layer responsibilities in a complete workflow.
5. Recognize that the same responsibilities can be ordered, combined, or placed differently on different platforms.
6. Explain that combining responsibilities in one tool hides the steps and does not remove them.
7. Explain that what a step knows depends on when it acts, so an arrangement can change a decision without changing the kind of result.
8. Explain that a device report can inform software only possibly, by policy, and not automatically.
9. Place the calls of an unfamiliar tool onto the responsibilities without relying on its names.
10. Say that SDKs, services, and products are not the same as responsibilities.
11. Describe where a hybrid loop fits: it repeats the send-and-return part, with the classical side deciding between passes.
12. Summarize Module 05 as a chain of responsibilities, and say what each page of the module taught.

## Experience-level scope

**Beginner (V1) teaches:** one computation through all the steps on both paths; what stays the same and what changes, computed from the models; three illustrative arrangements and what each step knows; the Control Layer's report as a possible, policy-dependent input; where the hybrid loop fits; architecture, not products; the module recap.

**Intermediate (future):** realistic cross-platform comparisons, including two real SDK workflows side by side; routing and placement applied to the circuit; the job and result objects in detail.

**Advanced (future):** performance analysis; heterogeneous integration; distributed runtimes; observability; latency and resource management.

Do not build Intermediate or Advanced content to make V1 more complete.

**Not on this page (any level):** SDK calls or comparisons of real SDKs (Module 03 and later depth), named services, platforms, or products, real status names, queue lengths, durations, prices, or limits, routing or placement algorithms, noise models, error correction (Module 07), calibration physics, algorithm design (Module 06), and cross-module links (deferred by the taxonomy).

## Main Interactive: "Workflow Explorer"

- **Controls (what the learner changes):**
  - target path: Simulator or Device Q4 (both invented, from 05.04);
  - arrangement: Prepare, then send; Send, then the service prepares; One tool does it all (each with a one-line description);
  - on the device path only: a newer report arrives while the job waits: No or Yes;
  - Step, Back, and Reset.
- **Display, kept in separate places:**
  - **the steps** (derived): the ordered list for this path and arrangement, each with its responsibility, group tag, who performs it, and a "done" or "now" mark;
  - **the step in focus** (derived): what it received and what it produced, from the model (the instruction list, the target's list, the adapted list, the job and its status, the method or device, the counts and the numbers made from them);
  - **what it knew** (derived, for the deciding steps): the report it had (time and status), the policy, and the pair that policy would choose, labelled as a possible decision that is not applied;
  - **the result** (observed): the counts with the invented and simulated tags, the numbers made from them, and a sentence saying that the arrangement changed who did what and what a step knew, and did not change the kind of result.
- **Cause, response, observation:** path, arrangement, and the report switch are the cause; the steps and what each knew are the response; what stays the same across arrangements and what differs is the observation.
- **Rules the page keeps:** every artifact comes from a shared module; every invented or simulated value is labelled; no clock or duration; the pair is shown, not applied; no claim that a report changes the counts; no vendor or product names.
- **Accessibility:** controls are real buttons; the steps are an ordered list; a text description gives each step in words; an aria-live region announces the step, who performs it, and what it produced; focus stays where it was after a re-render; tables are real tables with stacked rows on a phone.
- **Scope fence:** no SDK, no routing or placement, no named platform, no timing, no noise model, no hybrid-loop demonstration.

### Checks

## Important pedagogical constraints (draft)

Do not imply:
- `THE STACK = ONE FIXED PIPELINE`. The page shows three arrangements of the same responsibilities, and none is the way.
- `COMBINED = REMOVED`. A tool that does everything in one call still performs every step.
- `A DIFFERENT ARRANGEMENT = A DIFFERENT KIND OF RESULT`. It changes who does what and what each step knew. The result is still counts.
- `A DEVICE REPORT = AUTOMATIC IMPROVEMENT`. The report may inform a decision, by policy, and the page does not model how the decision changes the counts.
- `THE PAGE'S ARRANGEMENTS = HOW ANY REAL PLATFORM WORKS`. They are examples. The page names no platform.
- `A RESPONSIBILITY = A PRODUCT OR AN SDK`. Tools expose, combine, or leave out responsibilities.
- `THE SIMULATOR PATH = THE DEVICE PATH WITHOUT THE REPORT`. The target, the description, the adaptation, and the lifecycle differ too.
- `A SIMULATOR'S RESULT = A FORECAST OF THE DEVICE'S` (carried from 05.05).
- That a loop is better than a single run, or any claim about quantum advantage.

Do not teach here: SDK use or comparison of real SDKs, named platforms, routing or placement, timings, noise models, algorithm design, error correction, or calibration physics.

## End state (draft)

The learner leaves with: `ONE COMPUTATION → THE SAME RESPONSIBILITIES ON EVERY PATH → DIFFERENT TARGETS, DIFFERENT DESCRIPTIONS, DIFFERENT ARRANGEMENTS → NO ONE UNIVERSAL ORDER`.

Takeaway: *A quantum software stack is a set of responsibilities that describe a program, adapt it to a target, run it, and return the results. The simulator path and the device path share most of them, platforms arrange and combine them differently, and what each step knows depends on when it acts. A tool that hides the steps still performs them.*

Ends the module with "End of Module 05", a link to the Module 05 overview, and the closing question: "Given a tool you have never used, how would you find out which responsibilities it performs and which it leaves to you?"
