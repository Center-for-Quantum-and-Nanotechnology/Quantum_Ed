## Open questions for review

Each has a recommendation. Say which you accept or change; the rest of the draft already assumes the recommendations.

1. **How is one dense page organized?** The taxonomy fixes seven pages and forbids a separate control-software page, so capabilities, the simulator/device distinction, the control-software boundary, why calibration is done, and the telemetry fields all live here. *Recommendation:* **one page in two halves joined by one question.** First half: *what a target's description tells software* (operations, native gates, connectivity, simulator versus device). Second half: *what a device also reports, and why it changes* (calibration, telemetry, provenance). **One Main Interactive** in the middle, at the join, covers both halves. Nine subsections. Everything the taxonomy lists is kept; what is cut is breadth within each item (one device, one example circuit, a small set of fields shown with numbers).

2. **Which targets does the explorer offer?** *Recommendation:* **two targets**, both synthetic and labelled so: a **Simulator** (a classical program; its description lists its capabilities and limits, and it has no calibration data because nothing physical is calibrated) and a **Device** (a small invented device, "Device Q4", with qubits, connections, a native operation list, and **two labelled calibration snapshots**). In addition, subsection 2 shows the three 05.03 targets (Open, One-way CNOT, Rotations) as backend descriptions, to answer 05.03's closing question directly: *that list is a description of the target, supplied to software.*

3. **How big is the device, and does it break the Bell example?** A decision that depends on telemetry needs at least three qubits, so Bell alone cannot show it (the taxonomy allows an additional example here). *Recommendation:* **four invented qubits in a line (Q0–Q1–Q2–Q3, three connected pairs).** The Bell circuit stays the recurring example: it is the circuit whose placement the page asks about ("which connected pair could it use?"). The native operation list reuses the 05.03 **Rotations** vocabulary (turns about x and z, and a CNOT from the lower-numbered qubit to the higher), so the Bell circuit on any pair needs only the H-as-turns rewrite from 05.03. No routing, no qubit-mapping algorithm, no third qubit in the circuit. Choosing which physical qubits to use is named once, as something the glossary calls qubit mapping, which is Intermediate.

4. **Which telemetry fields get numbers?** The taxonomy lists eight categories. *Recommendation:* show **seven with synthetic numbers or labels** and **one by name only**:
   - qubit **operating frequency** (GHz), labelled modality-specific;
   - **T1** and **T2** (µs), each with an uncertainty, labelled as timescales that depend on how they were measured, with T2 and T2* **not** interchangeable (named, not both shown);
   - **single-qubit and two-qubit gate error** estimates (%), the two-qubit one per connected pair, labelled as protocol-dependent;
   - **readout assignment error**, shown as two numbers (a qubit prepared in 0 read as 1, and prepared in 1 read as 0), because the asymmetry is the qualification the taxonomy asks for and it is cheap to show;
   - **native operations and connectivity**, shown in the description half (capability metadata, which changes less often);
   - **timestamp, status, and uncertainty**, shown on every snapshot;
   - **pulse and control settings**, shown as one row, "Control settings: exist on the device; not reported here and not taught on this page", per the taxonomy ("recognize their existence").
   Every value is marked **synthetic**. The page says that other hardware types report different fields, and that no device reports every field every time.

5. **What is the synthetic data, and what must it show?** *Recommendation:* hand-authored, clearly synthetic, **different from Module 07's 9-qubit device** (new device, new numbers, a different name, so no one reads them as one machine). Designed to show, and pinned by tests, the things the page claims:
   - every qubit differs from the others (spatial variation);
   - between the two snapshots, **most values change a little, one changes a lot, and one improves** (so the page does not imply drift always means worse);
   - **one value is "not reported" in the later snapshot** (no device reports everything every time);
   - **the best connected pair changes between snapshots** under one stated policy, and **two stated policies disagree in the earlier snapshot** (so "what to do" depends on policy, not only on the numbers).
   A first sketch that meets all four (to be fixed and tested at build, not final): frequencies near 5.0 to 5.2 GHz; T1 from about 40 to 90 µs; readout error 1 to 3 %; two-qubit error 0.6 to 1.2 % per pair. Under "lowest two-qubit error on the pair", the earlier snapshot picks Q1–Q2 and the later picks Q2–Q3; under "lowest sum of the pair's two-qubit error and both readout errors", the earlier picks Q0–Q1 and the later picks Q2–Q3.

6. **How is "what software might do" shown without implying it is automatic?** The taxonomy requires reported data, software interpretation, and hypothetical response to be separate, and any consequence to be "a possible policy-dependent decision". *Recommendation:* three side-by-side panels in the explorer, each labelled and styled differently: **Reported** (the numbers, in the established teal-dashed telemetry style, with their time stamp and status), **What it means** (a plain sentence per field, always with its qualification: "T1 is a timescale, not the chance that a circuit succeeds"), and **A possible response** (dotted border and a tag "one possible policy"). The response panel states two policies and what each would pick for the Bell circuit, and says: *many tools do not do this automatically; whether and how a platform uses reported data depends on the platform.* There is **no predicted success probability anywhere**: the response is a ranking of reported numbers, and the panel says it is not a prediction.

7. **Stale and incomplete data.** The taxonomy says telemetry may be periodic, stale, estimated, or provider-filtered. *Recommendation:* the learner's choice of snapshot is framed as **"which report the software has"**: choosing the earlier snapshot while a later one exists is shown as software working from older data, with its age stated ("12 hours before the later snapshot"). The later snapshot's missing T2 is shown as "not reported". No live feed, no clock, no real dates.

8. **Capabilities versus calibration.** *Recommendation:* the page keeps two kinds of information visibly apart: **capability metadata** (native operations, connectivity: a solid-edged "backend description" card, the left-bar "where the groups meet" style from 05.01) and **calibration telemetry** (reported measurements and estimates: teal dashed). Say that capability metadata tends to change less often. Do not say how often anything changes.

9. **Where does the code live?** *Recommendation:* a **new pure module `QedBackend` (`backend.js`)**: target descriptions as data (kind: simulator or device; qubits; connected pairs; native operations), the **field catalog** (id, label, unit, scope, meaning, qualification, modality note), the two snapshots with provenance, `report(device, snapshotId)`, `change(device, fromId, toId)` (per value: unchanged, small, large, improved, not reported), `POLICIES`, and `choosePair(device, snapshotId, policy)`. Plus a small **device map renderer** (`deviceSVG`: qubits in a line, connections, a chosen pair marked by a text label and an outline). It has no dependencies. The capability part uses the **same `allows` shape as `QedTransform` targets**, so the 05.03 targets can be shown as backend descriptions without conversion and 05.07 can reuse both. Page-local: the explorer wiring, the field wording, and the checks.

10. **Experience levels.** *Recommendation:* as on 05.02 and 05.03, **V1 is Beginner-only with no gated blocks**, because basic telemetry literacy is Beginner by the taxonomy. Intermediate (future): detailed telemetry schemas and uncertainty, calibration-aware compilation policies, per-gate and per-time-slot data. ## Goal

Teach the learner that software describes each target to itself, that this description tells software what the target allows and, for a device, what has been reported about its current condition, and that reported values are time-stamped estimates which can change and are not guarantees.

Central progression:

`A TARGET'S LIST COMES FROM A DESCRIPTION → A DESCRIPTION SAYS WHAT A TARGET ALLOWS → A DEVICE IS CALIBRATED BECAUSE ITS BEHAVIOR DRIFTS → CALIBRATION TELEMETRY REPORTS ESTIMATES WITH A TIME → SOFTWARE MAY USE THEM UNDER A POLICY`

Key conceptual transition: **"A target is not just a list of allowed operations. It is a description that software reads, and for a device the description can include time-stamped estimates of how each part is doing. Those numbers inform decisions. They do not guarantee outcomes."**

It opens by answering the question 05.03 ended on ("where does a target's list of what it allows come from, and could it change?") and ends by asking the question that motivates 05.05.

## Learning outcomes (Beginner)

The learner should be able to:

1. Explain that software reads a backend description of a target to learn what it allows, and that this is where a target's list of operations comes from.
2. Name what a description of a target communicates: supported operations (native gates), which qubits can be used together (connectivity), and the kind of target.
3. Distinguish a simulator target from a hardware device target, including that a simulator has no calibration data because nothing physical is calibrated.
4. Distinguish calibration (a procedure that characterizes and tunes a device) from calibration telemetry (information reported about its condition).
5. Explain why devices are calibrated and why reported characteristics change over time (drift), including that change is not always for the worse.
6. Describe the boundary between application-facing software and device-control software, and recognize that control settings exist without being taught or exposed here.
7. Read a small set of telemetry fields, with units: operating frequency, T1, T2, gate error, readout error, and what each is an estimate of.
8. Explain that each reported value carries a time, a status, and an uncertainty, and that a number without them can mislead.
9. Distinguish what was reported, what it means, and what software might do about it, and say that a response depends on a policy.
10. Explain that a metric is not a guarantee: T1, gate error, or readout error alone does not say whether a whole circuit will succeed.
11. Explain that reported data may be old, incomplete, or estimated, and that not every device reports every field.
12. Distinguish backend metadata from raw control signals, and drift from automatic adaptation.
13. Ask how a simulator, as one kind of target, works out its answer.

## Experience-level scope

**Beginner (V1) teaches:** that software describes targets; what a description communicates (operations, connectivity, kind of target); simulator versus device targets; why calibration happens and the boundary to control software; the telemetry fields in the table of question 4, with units, meaning, and qualification; provenance (time, status, uncertainty); drift between two snapshots; reported data, its meaning, and a possible policy-dependent response, kept apart; the five misconceptions in the taxonomy.

**Intermediate (future):** detailed telemetry schemas and their uncertainty; calibration-aware compilation and scheduling policies; per-time-slot and per-gate data; comparing two providers' descriptions.

**Advanced (future):** pulse and control interfaces; real platform software–hardware boundaries; closed-loop recalibration and monitoring.

Do not build Intermediate or Advanced content to make V1 more complete.

**Not on this page (any level):** calibration physics and measurement protocols (Quantum Hardware), pulse design or control electronics, real vendor field names, schemas, or APIs, real device values or "typical" ranges, SDK calls, hardware-aware decoding (Module 07), routing or qubit-mapping algorithms (Intermediate), simulation methods (05.05), job lifecycles (05.06).

## Page structure (draft)

1. **From Transformation to Targets.** Reconnect to 05.03: three targets, each with a list of what it allows, and the closing question ("where does that list come from, and could it change?"). Answer in one sentence: software reads a **description** of the target. Name what this page covers in the order it comes: what a description says, then what a device additionally reports and why it changes.

2. **What a Backend Description Tells Software.** The description as the place where the Application and Control groups meet (05.01). It says what the target is, what operations it allows (native gates), and which qubits can be used together (connectivity). Show the three 05.03 targets as descriptions: the same lists, now named as descriptions. Say the description is an abstraction: **not** raw control signals, and not the device itself.

3. **Simulator Targets and Device Targets.** Both have descriptions; they say different things. A simulator target: operations, limits set by the classical computer, no calibration data. A device target: operations, connectivity, and reported condition. The explorer's two targets, described side by side. One hedged sentence about imitating a device.

4. **Why a Device Is Calibrated, and Where the Control Software Sits.** Calibration is a **procedure** that characterizes and tunes a device; behavior can drift, so it is repeated. Control software (the Control Layer) runs it and sits beside the device; application-facing software sits on the other side of the backend description. Control settings exist (one labelled row) and are not taught. Calibration versus telemetry in one contrast. The physical reasons belong to the Quantum Hardware module (one sentence, no link yet).

5. **Reading Calibration Telemetry.** The fields from question 4, in a small set of cards or a table, each with: what it conveys, its unit, and **what it is not** ("T1 is a timescale, not the chance a circuit succeeds"; "gate error depends on how it was estimated"; "readout error can differ for 0 and 1"). Every value is marked synthetic. Then **provenance**: a value comes with a time, a status, and an uncertainty; show a number with and without them.

6. **Main Interactive: "Backend and Calibration Explorer."** The learner chooses a target (Simulator or Device Q4) and, for the device, which snapshot the software has (Earlier or Later). Select a qubit or a connection on the device map to see its fields. Three separate panels: **Reported**, **What it means**, **A possible response**. A comparison view shows what changed between the two snapshots. Resettable and keyboard accessible. See below.

7. **A Metric Is Not a Guarantee, and Telemetry Is Not Live Truth.** A contrast block for the taxonomy's misconceptions: calibration ≠ telemetry; a metric ≠ a guarantee (a whole circuit's success depends on much more than one number); telemetry ≠ real-time truth (periodic, old, estimated, filtered, incomplete); backend metadata ≠ control signals; drift ≠ automatic adaptation.

8. **From Reported Numbers to Possible Decisions.** The Bell circuit and a question: "which connected pair could it use?" Two stated policies, each choosing a pair from the same snapshot, which may disagree; the same policy choosing differently from the other snapshot. The point: **what software does depends on its policy and on which report it has**, and many tools do not do this automatically. Do not teach mapping or routing.

9. **From Targets to Simulators.** Bridge. The simulator appeared in the explorer as one kind of target, with no calibration data. ## Main Interactive: "Backend and Calibration Explorer"

- **Controls:**
  - target: Simulator, Device Q4 (each with a one-line description, both labelled synthetic);
  - snapshot (Device only): Earlier, Later, each labelled with its synthetic time ("06:00" and "18:00, same day"); for the Simulator the control is shown disabled with the reason: "a simulator has no calibration data";
  - select a qubit or a connection on the device map (buttons);
  - a view toggle, "Compare the two snapshots", showing each value's change;
  - reset.
- **Display, kept in three separate places:**
  - **Reported** (teal dashed, tagged "reported"): the selected item's values with units, uncertainty, the snapshot's time and status, and "not reported" where a value is missing;
  - **What it means:** a plain sentence per field with its qualification;
  - **A possible response** (dotted border, tagged "one possible policy"): for the Bell circuit, the pair each of two stated policies would choose from this snapshot, and a sentence that this is a ranking of reported numbers, not a prediction.
  - the **backend description** (capabilities) in its own solid-edged card, separate from all three.
- **Cause, response, observation:** target, snapshot, and selection are the cause; the description and the panels are the response; what the learner notices (a value moved, policies disagree, a pair changed) is the observation.
- **Rules the page keeps:** every value says it is synthetic; every value shows its time; a missing value reads "not reported" and is never filled in; the response panel never shows a success probability; changes are shown with a text word ("higher", "lower", "about the same") and an arrow glyph, never color alone; "improved" is shown as readily as "worse".
- **Accessibility:** controls are buttons; the device map's qubits and connections are keyboard-focusable buttons with text labels; every table is real text; an aria-live region announces a change of target, snapshot, or selection; the comparison is available as a list of sentences.
- **Scope fence:** no real device or vendor, no real field names or API, no pulse or control values, no live data, no routing, no success prediction.

### Checks

- *Transfer task:* "Software has the earlier snapshot, and the later one now exists. What might go wrong if it uses the earlier one?" (values may have drifted; the best pair may have changed).

## Important pedagogical constraints (draft)

Do not imply:
- `CALIBRATION = TELEMETRY`. Calibration is a procedure; telemetry is reported information.
- `A METRIC = A GUARANTEE`. T1, gate error, or readout error alone cannot predict whether a whole workload succeeds.
- `TELEMETRY = CONTINUOUS REAL-TIME TRUTH`. Values may be periodic, old, estimated, filtered, or missing.
- `BACKEND METADATA = RAW CONTROL SIGNALS`. A description is an abstraction.
- `DRIFT = AUTOMATIC ADAPTIVE COMPILATION`. A response depends on the platform, its data access, its policies, and its software.
- That any device reports every field, or that the fields shown are a standard schema. Fields differ by hardware type and provider.
- That the synthetic device or its numbers are real, typical, or any vendor's.
- That "lower error" or "longer T1" is simply "better" for a whole circuit, or that drift always makes things worse.
- That a simulator and a device are described the same way, or that a simulator has hardware properties.
- That the Control Layer and the backend description are the same thing, or that application software talks to control electronics.

Do not teach here: calibration physics or measurement protocols, pulse design, real vendor schemas or APIs, hardware-aware decoding, routing or qubit-mapping algorithms, simulation methods, job lifecycles, or any real SDK behavior.

## End state (draft)

The learner leaves with: `SOFTWARE READS A DESCRIPTION OF EACH TARGET → A DEVICE IS CALIBRATED AND REPORTS TIME-STAMPED ESTIMATES → THOSE NUMBERS CAN CHANGE, AND ARE NOT GUARANTEES → SOFTWARE MAY USE THEM UNDER A POLICY, OR NOT AT ALL`.

Takeaway: *A backend description tells software what a target allows. For a device it can also carry time-stamped estimates from calibration. They change over time, they are not guarantees, and what software does with them depends on its policy.*
